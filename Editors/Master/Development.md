## 1. Назначение

- уже достаточно важны, чтобы не потеряться;
- относятся к развитию Master или отношений между системами;
- ещё не прошли достаточную практическую проверку;
- не должны преждевременно становиться нормой.

# 3. System → Master Feedback Protocol

**Status:** 🧪 Testing

## 3.1. Проблема

Системные проблемы и идеи развития могут возникать непосредственно во время работы:

- у редактора;
- внутри VIA;
- внутри Research;
- в Distribution;
- во время Experiment;
- в другой системе In Profundo.

Если каждое такое наблюдение немедленно прерывает рабочий процесс, развитие начинает мешать производству.

Если наблюдение просто остаётся внутри ответа редактора, оно легко теряется.

Необходим лёгкий механизм:

> **зафиксировать системно значимое наблюдение, не останавливая нормальный процесс без необходимости.**

---

## 3.2. System Signal

Любой Editor или System может обнаружить вопрос, выходящий за пределы своей локальной задачи.

Например:

- повторяющаяся проблема процесса;
- неясность документации;
- конфликт ролей;
- недостаток компетенции;
- повторяющаяся ручная операция;
- потенциальное улучшение;
- противоречие документов;
- проблема handoff;
- необходимость новой функции;
- вопрос, выходящий за полномочия системы.

Если вопрос не блокирует текущую работу, Editor завершает основную задачу и добавляет сигнал.

Рабочая форма:

```markdown
## 🔴 System Signal

**Observation:**  
Что произошло или было замечено.

**Why it matters:**  
Почему вопрос может выходить за пределы текущей локальной задачи.

**Evidence / Source:**  
Где это проявилось.

**Urgency:**  
Non-blocking / Blocking

**Suggested target:**  
Если понятно — какой документ, роль или система потенциально затронуты.
```

`Suggested target` является предложением источника сигнала, а не архитектурным решением.

---

# 4. Non-blocking Signal

По умолчанию системный сигнал не должен останавливать основной процесс.

```text
EDITOR
   ↓
выполняет задачу
   ↓
обнаруживает проблему
   ↓
🔴 SYSTEM SIGNAL
Non-blocking
   ↓
фиксирует
   ↓
основной процесс продолжается
```

Рабочий принцип:

> **Development не должно постоянно останавливать Production.**

---

# 5. Blocking Signal

Если продолжение работы требует решения за пределами полномочий системы, сигнал становится блокирующим.

Например:

- отсутствует необходимое стратегическое решение;
- Input недостаточен для понимания смысла задачи;
- выполнение потребует нарушения явно установленной Boundary;
- существуют противоречащие друг другу обязательные инструкции.

В таком случае система не должна самостоятельно достраивать решение более высокого уровня.

Рабочая форма:

```markdown
## 🔴 Master Review Required — Blocking

**Blocked task:**  
Что невозможно корректно продолжить.

**Missing decision / clarity:**  
Чего именно не хватает.

**Why this exceeds local authority:**  
Почему система не должна решить вопрос самостоятельно.

**Required from Master:**  
Какой уровень ясности необходим для продолжения.
```

---

# 6. Cycle Observation

Если сигналы не блокируют процесс, они собираются до завершения соответствующего цикла.

Роль или Editor, отвечающий за финальное закрытие, должен учитывать:

- собственные наблюдения;
- System Signals предыдущих участников;
- повторяющиеся проблемы;
- связанные сигналы разных редакторов.

Он не просто перечисляет все замечания, а по возможности:

- объединяет дублирующие сигналы;
- различает локальные и системные вопросы;
- указывает доказательства;
- предлагает место дальнейшего рассмотрения.

Рабочая модель:

```text
Editor A Signal ───┐
                   │
Editor B Signal ───┤
                   ├──► CYCLE OBSERVATION
Editor C Signal ───┤
                   │
Closer Observation ┘
```

---

# 7. Cycle Development Summary

По завершении цикла Owner должен получать не россыпь отдельных замечаний, а компактный пакет развития.

Рабочая форма:

```markdown
## Cycle Development Summary

### 🔴 Master Review Required

#### 1. [Название вопроса]

**Observed by:**  
Какие роли / этапы обнаружили проблему.

**Pattern:**  
Одиночное наблюдение или повторяющаяся проблема.

**Evidence:**  
Где это проявилось.

**Why systemic:**  
Почему вопрос выходит за пределы локальной правки.

**Potentially affected:**  
Какие роли, документы или системы могут быть затронуты.

**Recommended transfer:**  
Куда перенести вопрос для дальнейшего рассмотрения.

---

### Local Observations

Наблюдения, которые могут быть возвращены соответствующей системе без Master-level review.
```

# 8. Owner as Physical Bridge

На текущем этапе Owner часто остаётся физическим мостом между:

- чатами редакторов;
- GitHub;
- Notion;
- отдельными системами.

Цель протокола — уменьшить интеллектуальную нагрузку Owner даже тогда, когда физический перенос остаётся ручным.

Editor / System должен по возможности подготовить:

```text
WHAT
что нужно передать

WHY
почему

SOURCE
откуда

TARGET
куда

READY BLOCK
что именно перенести
```

Тогда функция Owner сводится преимущественно к:

> **перенести готовый пакет в указанное место**, а не реконструировать проблему самостоятельно.

В будущем этот handoff может быть частично автоматизирован.

Автоматизация не должна проектироваться до стабилизации самого контракта передачи.

# 9. Master Intake

После передачи System Signal Master не обязан автоматически принимать предложенную классификацию.

Master определяет:

```text
SYSTEM SIGNAL
      ↓
MASTER REVIEW
      │
      ├── LOCAL
      │      ↓
      │   вернуть системе
      │
      ├── DEVELOPMENT
      │      ↓
      │   сохранить / исследовать
      │
      ├── EXPERIMENT
      │      ↓
      │   проверить гипотезу
      │
      ├── DOCUMENTATION
      │      ↓
      │   практика уже достаточно зрелая
      │
      └── STRATEGIC
             ↓
      🔴 Strategic Decision Required
             ↓
           OWNER
```

Система, обнаружившая проблему, отвечает прежде всего за качественную диагностику.

Она не обязана проектировать архитектурное решение.

# 10. Два направления красного сигнала

Рабочая гипотеза:

```text
SYSTEM → MASTER
🔴 System Signal /
Master Review Required

MASTER → OWNER
🔴 Strategic Decision Required
```

Красный цвет в обоих случаях означает:

> **вопрос выходит за пределы полномочий текущего уровня и не должен быть потерян или молча решён на неправильном уровне.**

Направление определяется подписью сигнала.

Эта модель требует практической проверки до превращения в общий стандарт In Profundo.

# 11. Downstream Strategy Leakage

**Status:** 🧪 Testing

Pilot-003 показал потенциально важный паттерн:

```text
upstream ambiguity
       ↓
weak handoff
       ↓
downstream must act
       ↓
downstream fills missing meaning
       ↓
appears to exceed authority
```

Рабочая гипотеза:

> **Нарушение границ downstream-системы может быть вызвано не только чрезмерной автономией downstream, но и недостаточной определённостью upstream-handoff.**

Поэтому перед ограничением роли необходимо проверить качество её Input.

# 13. Stage Colleges

**Status:** 💡 Concept

Рабочая идея:

> вместо ручного последовательного включения большого числа отдельных Editors на некоторых этапах может работать Stage College, получающий один Input Package и возвращающий один интегрированный Output Package.

Потенциальная цель:

- уменьшить ручную диспетчеризацию Owner;
- сделать границы этапов яснее;
- собрать несколько компетенций вокруг одной задачи;
- сохранить независимость профессиональных перспектив без множества отдельных handoff.

Не решено:

- является ли College отдельной сущностью или режимом композиции Editors;
- кто интегрирует результаты;
- на каких этапах College действительно полезен;
- не создаст ли College дополнительную бюрократию;
- одинаковая ли модель подходит Portfolio, Review, Publication и Distribution.

Следующий разумный уровень:

```text
не создавать полную архитектуру Colleges
        ↓
выбрать один подходящий Stage
        ↓
провести ограниченный Experiment
        ↓
сравнить:
нагрузку
качество
понятность
число handoff
```

# 20. Development Exit

Вопрос не должен оставаться в `Development.md` навсегда.

Возможные выходы:

```text
DEVELOPMENT ITEM
       ↓
       ├── ⚪ PARKED
       │
       ├── 🧪 EXPERIMENT
       │
       ├── 🔴 OWNER DECISION
       │
       ├── 🟢 DOCUMENTATION
       │
       └── CLOSED / REJECTED
```

Когда концепция проверена, она должна перейти в соответствующее постоянное место.

Например:

```text
Master cognition
→ Thinking_Framework / Operating_Model

system boundary
→ Project_Map / system docs

accepted architectural decision
→ Decision_Memory + relevant docs

working process
→ Workflow / role documentation

experimental evidence
→ Experiment / Pilot archive
```

`Development.md` должен оставаться пространством живого развития, а не архивом завершённых вопросов.

# 21. Текущие приоритеты проверки

На текущем этапе наиболее полезно наблюдать практику в следующих областях:

### 1. System Signal Protocol

Проверить на реальном редакционном или исследовательском цикле:

- замечают ли Editors системные вопросы;
- понятен ли формат сигнала;
- не начинает ли красный сигнал чрезмерно прерывать производство;
- способен ли Cycle Closer собрать несколько сигналов в один Development Summary.

### 2. Master Handoff / Transfer Threshold

Проверить:

- достаточно ли короткого Handoff;
- понимает ли downstream-система свою задачу без дополнительного стратегического объяснения;
- не переоткрывает ли upstream-решения.

### 3. Content Portfolio → Coach → VIA

Проверить модель на нескольких последовательных материалах.

### 4. Research Quality Function

Провести функциональную диагностику до обсуждения отдельной роли.

### 5. Stage College

Не развивать архитектуру теоретически до появления подходящего ограниченного Experiment.

# 22. Центральный принцип Development

> **Development хранит не всё, что можно улучшить, а то, что требует обучения системы прежде, чем станет правилом.**

Master должен стремиться не быстрее стандартизировать возникающие идеи, а быстрее определить:

> какой следующий опыт позволит принять более качественное решение.
