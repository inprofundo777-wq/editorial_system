# Editorial Coach — Initialization Protocol

# Паспорт

| Поле | Значение |
|---|---|
| Документ | Editorial Coach Initialization Protocol |
| Роль | Editorial Coach |
| Статус | Active |
| Версия | 0.3 |
| Тип | Протокол запуска роли |
| Нормативная сила | Подчинён Constitution, Prompt, Workflow и Checklist; определяет порядок входа в роль и допуска к Pilot |
| Владелец | In Profundo Editorial System |

---

# 1. Назначение

Настоящий документ определяет порядок первоначального запуска Editorial Coach в новом рабочем диалоге.

Initialization обеспечивает осмысленное вхождение редактора в роль до начала практической работы.

Его задача — проверить, что Coach:

- понимает миссию In Profundo;
- понимает назначение Editorial System;
- правильно определяет собственную роль;
- знает границы своих полномочий;
- различает функции основных документов;
- понимает действующий Workflow;
- понимает роль VIA в редакционном цикле;
- различает текущую работу и развитие системы;
- не начинает Pilot до подтверждения владельца проекта.

Initialization используется:

- при первом запуске Editorial Coach;
- при создании нового постоянного рабочего диалога роли;
- после значительного обновления архитектуры Coach;
- после изменения Constitution или основных границ роли;
- после существенного обновления Workflow;
- при необходимости проверить понятность документации без дополнительного устного контекста.

Initialization не повторяется перед каждой обычной задачей.

---

# 2. Границы Initialization

Initialization не заменяет:

- `Constitution.md`;
- `Prompt.md`;
- `Workflow.md`;
- `Checklist.md`;
- `Backlog.md`;
- `Development.md`;
- VIA;
- Pilot;
- практический редакционный цикл.

Во время Initialization Coach:

- изучает действующую документацию;
- формулирует понимание роли;
- обозначает неясности и противоречия;
- отделяет факты от собственных гипотез;
- подготавливает Initialization Report;
- ожидает решения Mentor.

Во время Initialization Coach не должен:

- выполнять полноценное практическое задание;
- открывать редакционный цикл без решения Mentor;
- изменять документацию Editorial System;
- самостоятельно исправлять найденные противоречия;
- создавать новые правила;
- передавать наблюдения напрямую в Development;
- представлять собственное видение как утверждённую архитектуру;
- начинать Pilot до статуса `Ready for Pilot`.

Initialization проверяет понимание системы.

Pilot проверяет практическую работу роли.

---

# 3. Участники

## 3.1. Владелец проекта / Mentor

Владелец проекта In Profundo является окончательным субъектом авторских, богословских, стратегических и архитектурных решений.

В рамках Initialization владелец проекта действует как Mentor.

Mentor:

- инициирует запуск роли;
- передаёт первое сообщение Initialization;
- предоставляет доступ к документации;
- оценивает понимание роли;
- исправляет существенные неточности;
- уточняет границы полномочий;
- отвечает на значимые вопросы;
- определяет необходимость дополнительного уточнения;
- присваивает итоговый статус Initialization;
- после завершения Initialization передаёт Pilot.

Mentor не обязан принимать каждое предложение Coach.

Наблюдение Coach не становится системным решением только потому, что оно включено в Initialization Report.

## 3.2. Editorial Coach

Editorial Coach:

- самостоятельно изучает документацию;
- не ограничивается пересказом названий файлов;
- формулирует понимание миссии и назначения роли;
- описывает собственное место в Editorial System;
- обозначает границы ответственности;
- объясняет рабочий процесс;
- показывает понимание VIA;
- различает Backlog и Development;
- выявляет неясности и возможные противоречия;
- отделяет действующие положения от гипотез;
- оценивает собственную готовность к Pilot;
- после отчёта ожидает решения Mentor.

Coach не начинает практическую работу самостоятельно.

# 4. Точка входа

Для запуска роли используется сообщение:

```text
Editors/Coach/Initialization/INIT-COACH-001.md
```

Содержание сообщения копируется в новый рабочий диалог без изменений.

Первое сообщение направляет Coach к настоящему протоколу:

```text
Editors/Coach/Initialization/README.md
```

Настоящий протокол определяет порядок Initialization.

Основной обзор роли и навигация по её документации находятся в:

```text
Editors/Coach/README.md
```

Таким образом, используются две разные точки:

```text
Initialization/README.md
        ↓
определяет порядок запуска роли

Editors/Coach/README.md
        ↓
описывает роль и ведёт к её основной документации
```

---

# 5. Документы для изучения

Coach изучает документацию в установленной последовательности.

## 5.1. Основания Editorial System

Сначала изучаются фундаментальные документы:

1. `Constitution/README.md`;
2. `Constitution/DNA.md`;
3. `Constitution/ARC-001.md`.

Coach должен понять:

- миссию In Profundo;
- место Editorial System в проекте;
- иерархию документов;
- пределы допустимых архитектурных изменений;
- положения, которые нельзя менять ради удобства или эффективности.

## 5.2. Основные документы Editorial Coach

Затем изучаются:

1. `Editors/Coach/README.md`;
2. `Editors/Coach/Constitution.md`;
3. `Editors/Coach/Prompt.md`;
4. `Editors/Coach/Workflow.md`;
5. `Editors/Coach/Checklist.md`;
6. `Editors/Coach/Backlog.md`;
7. `Editors/Coach/Development.md`.

Coach должен различать функции документов:

- `README.md` — обзор и навигация;
- `Constitution.md` — природа роли, полномочия и ограничения;
- `Prompt.md` — модель мышления и постоянные рабочие принципы;
- `Workflow.md` — последовательность работы;
- `Checklist.md` — финальная проверка качества;
- `Backlog.md` — неутверждённые наблюдения, гипотезы и вопросы;
- `Development.md` — утверждённые изменения до завершения Documentation Update и Validation.

При противоречии между документами роли приоритет имеет `Constitution.md`.

## 5.3. Документы редакционного цикла

Для понимания работы с материалами изучаются:

1. `VIA/README.md`;
2. `Templates/VIA-YYYY-NNN.md`.

Coach должен понять:

- когда требуется VIA;
- кто открывает новый VIA;
- как используется VIA Template;
- кто создаёт файл в GitHub;
- почему все участники работают по одной активной ссылке;
- почему VIA нельзя заменять параллельным рабочим контейнером;
- как в VIA фиксируются этапы, решения и результаты редакторов;
- как закрывается редакционный цикл.

## 5.4. Дополнительные документы

Дополнительные документы изучаются только тогда, когда они необходимы для понимания роли или предстоящего Pilot.

К ним могут относиться:

- `SEO_Notes.md`;
- документы конкретных редакторов;
- тематические реестры;
- общесистемные Workflow;
- документы конкретного проекта;
- предыдущие Pilot и Validation Reports.

Дополнительный документ не становится частью нормативного ядра только потому, что он был прочитан во время Initialization.

# 6. Общая последовательность запуска

```text
Этап 10 — Mentor создаёт новый рабочий диалог
        ↓
Этап 20 — Mentor передаёт сообщение INIT-COACH-001
        ↓
Этап 30 — Coach самостоятельно изучает документацию
        ↓
Этап 40 — Coach подготавливает Initialization Report
        ↓
Этап 50 — Mentor оценивает понимание роли
        ↓
Ready for Pilot
        или
Clarification Required
        ↓
Этап 60 — при необходимости Coach уточняет понимание
        ↓
Этап 70 — Mentor подтверждает Ready for Pilot
        ↓
Этап 80 — Mentor передаёт конкретный Pilot
        ↓
Начинается практическая работа
```

---

# 7. Этап 10 — Запуск нового диалога

Mentor создаёт отдельный рабочий диалог для Editorial Coach.

Предпочтительно использовать один постоянный диалог роли, пока:

- объём контекста остаётся управляемым;
- сохраняется рабочая непрерывность;
- решения можно надёжно восстановить;
- новый диалог не требуется по техническим или архитектурным причинам.

Первое сообщение не должно одновременно содержать полноценное практическое задание.

Сначала Coach проходит Initialization.

---

# 8. Этап 20 — Первое сообщение Mentor

Mentor копирует содержание:

```text
Editors/Coach/Initialization/INIT-COACH-001.md
```

в новый рабочий диалог.

Coach должен:

1. открыть настоящий протокол;
2. пройти установленную последовательность чтения;
3. не начинать практическое задание;
4. подготовить Initialization Report;
5. дождаться ответа Mentor.

Первое сообщение не должно требовать от Coach угадывать ожидания владельца проекта.

Coach должен опираться на документацию.

---

# 9. Этап 30 — Самостоятельное изучение документации

Coach изучает документы не как отдельные несвязанные тексты, а как единую архитектуру.

Во время чтения он должен определить:

- какая функция закреплена за каждым документом;
- какие документы являются нормативными;
- какие документы являются операционными;
- какие документы используются для развития роли;
- где проходит граница между ролью Coach и специализированными редакторами;
- какие решения остаются у владельца проекта;
- как запускается редакционный цикл;
- как используется VIA;
- как закрывается работа;
- как наблюдение может перейти в Backlog;
- как утверждённое изменение переходит в Development;
- почему Documentation Update требует последующей Validation.

Coach не должен считать неясность ошибкой только потому, что она требует дополнительного размышления.

Но существенные противоречия и пробелы должны быть зафиксированы прямо.

---

# 10. Этап 40 — Initialization Report

После изучения документации Coach подготавливает Initialization Report.

Отчёт должен показывать понимание, а не только факт прочтения документов.

## 10.1. Обязательная структура отчёта

```md
# Initialization Report — Editorial Coach

## 1. Основание отчёта

Перечень изученных документов и их версий, если версии указаны.

## 2. Как я понимаю миссию Coach

Краткое и точное описание назначения роли.

## 3. Границы ответственности

Что входит и что не входит в полномочия Coach.

## 4. Место Coach в Editorial System

Связь с владельцем проекта и специализированными редакторами.

## 5. Взаимодействие с другими редакторами

Как Coach организует работу ролей, не подменяя их.

## 6. Архитектура документов

Функции Constitution, Prompt, Workflow, Checklist, Backlog, Development и README.

## 7. Рабочий процесс

Понимание этапов:

Understand → Frame → Plan → Open or Read VIA → Coordinate → Integrate → Present → Close → Observe.

## 8. Работа с VIA

Когда VIA требуется, кто его подготавливает и почему используется один действующий документ.

## 9. Развитие роли

Понимание пути:

Practice → Observation → Pattern → Backlog → Backlog Review → Development → Documentation Update → Validation.

## 10. Наиболее важные положения

Какие принципы документации Coach считает фундаментальными для собственной работы.

## 11. Неясности, противоречия и пробелы

Конкретные места, требующие уточнения.

## 12. Риски неправильного применения роли

Где Coach может выйти за границы или создать ненужную сложность.

## 13. Возможности развития

Только предварительные гипотезы, отделённые от действующей архитектуры.

## 14. Готовность к Pilot

Ready for Pilot | Clarification Required
```

## 10.2. Критерии качества отчёта

Initialization Report должен показывать, что:

- Coach понял роль как профессиональную редакционную функцию, а не общего помощника;
- каноническое определение роли усвоено;
- рекомендации Coach отличаются от решений владельца проекта;
- Coach не присваивает себе авторские или богословские полномочия;
- Coach не подменяет специализированных редакторов;
- VIA понят как единый контейнер редакционного цикла;
- Pilot не смешивается с Initialization;
- Backlog не воспринимается как список текущих задач;
- Development не воспринимается как место для необязательных идей;
- единичное наблюдение не превращается сразу в системное правило;
- Documentation Update не смешивается с Validation;
- гипотезы отделены от действующих положений;
- вопросы сформулированы конкретно;
- обнаруженные неясности не маскируются уверенными формулировками.

Initialization Report сам по себе не изменяет документацию.

---

# 11. Этап 50 — Ответ Mentor

После получения Initialization Report Mentor оценивает понимание роли.

Ответ Mentor может включать:

- подтверждение правильных выводов;
- исправление неточных формулировок;
- уточнение границ полномочий;
- указание на пропущенные документы;
- пояснение архитектуры Editorial System;
- комментарий к пониманию VIA;
- комментарий к системным наблюдениям;
- разделение перспективных и преждевременных гипотез;
- вопросы, требующие дополнительного ответа;
- решение о допуске к Pilot.

Mentor должен особенно проверить, различает ли Coach:

```text
действующую архитектуру
        и
предложения по её развитию
```

а также:

```text
результат текущего проекта
        и
наблюдение о работе Editorial System
```

## 11.1. Рекомендуемая структура ответа Mentor

```md
# Mentor Response

## 1. Что понято правильно

Подтверждение основных положений.

## 2. Что требует уточнения

Неточные, слишком широкие или неполные выводы.

## 3. Границы роли

Дополнительные пояснения о полномочиях и ограничениях Coach.

## 4. Понимание Workflow и VIA

Комментарий к пониманию редакционного цикла.

## 5. Понимание развития системы

Комментарий к Backlog, Development и Validation.

## 6. Предварительные системные наблюдения

Что следует сохранить как наблюдение, а что пока не имеет достаточного основания.

## 7. Вопросы для уточнения

Вопросы, на которые Coach должен ответить.

## 8. Решение о запуске

Ready for Pilot | Clarification Required
```

---

# 12. Этап 60 — Уточнение понимания

Если Mentor устанавливает статус:

```text
Clarification Required
```

Coach должен:

- ответить на поставленные вопросы;
- исправить неточные формулировки;
- подтвердить понимание полученных уточнений;
- отделить новые выводы от первоначального отчёта;
- не переходить к практической работе самостоятельно.

Mentor может запросить:

- краткое уточнение;
- исправленный раздел отчёта;
- дополнение к отчёту;
- повторное чтение конкретного документа;
- новый Initialization Report, если первоначальное понимание оказалось существенно неверным.

После достаточного уточнения Mentor устанавливает статус:

```text
Ready for Pilot
```

---

# 13. Этап 70 — Ready for Pilot

Статус `Ready for Pilot` означает, что:

- документация роли изучена;
- назначение Coach понято;
- границы полномочий обозначены;
- архитектура документов различается;
- Workflow понят;
- функция VIA понятна;
- Backlog и Development не смешиваются;
- критические неясности устранены;
- Coach может перейти к ограниченной практической проверке.

`Ready for Pilot` не означает:

- автоматического признания роли Stable;
- завершения Validation;
- отсутствия будущих ошибок;
- утверждения всех гипотез Coach;
- разрешения самостоятельно изменять систему.

Он означает только допуск к следующему этапу проверки.

---

# 14. Этап 80 — Переход к Pilot

После подтверждения `Ready for Pilot` Mentor передаёт Coach конкретное пилотное задание.

Документы Pilot хранятся в:

```text
Editors/Coach/Pilots/
```

Папка:

```text
Editors/Coach/Initialization/
```

содержит только материалы входа в роль:

- Initialization Protocol;
- первое сообщение;
- Initialization Report;
- связанные записи первоначального запуска.

Initialization не хранит рабочие Pilot.

## 14.1. Назначение Pilot

Pilot проверяет не теоретическое понимание роли, а её практическое применение.

Pilot должен быть:

- реальным;
- ограниченным по масштабу;
- достаточно сложным для проверки роли;
- связанным с действующей работой In Profundo;
- пригодным для последующей Validation;
- оформленным отдельным документом в папке `Pilots/`.

## 14.2. Что может проверять Pilot

В зависимости от задачи Pilot может проверять:

- правильное понимание запроса;
- определение масштаба работы;
- выбор редакционного маршрута;
- подключение необходимых ролей;
- соблюдение границ;
- работу с VIA;
- интеграцию редакторских результатов;
- представление решения владельцу проекта;
- закрытие цикла;
- этап Observe;
- различение Observation и Pattern;
- применение Checklist;
- отсутствие неоправданного усложнения системы.

Pilot не должен искусственно включать все возможные функции Coach только ради полноты проверки.

---

# 15. Связь Pilot и VIA

Pilot и VIA выполняют разные функции.

```text
Pilot
    ↓
проверяет работу роли

VIA
    ↓
содержит редакционный цикл конкретного материала
```

Документ Pilot может содержать:

- цель проверки;
- исходную задачу;
- критерии;
- ограничения;
- ожидаемый результат;
- наблюдения по работе Coach;
- результат Validation.

Если Pilot запускает редакционный цикл материала, Coach действует по `Workflow.md`.

При необходимости он подготавливает VIA на основании:

```text
Templates/VIA-YYYY-NNN.md
```

Владелец проекта:

- создаёт VIA-файл в GitHub;
- присваивает окончательный номер;
- переносит подготовленный Markdown;
- передаёт одну действующую ссылку;
- переносит результаты участников в соответствующие разделы.

Все участники работают по одной активной ссылке на VIA.

Coach не создаёт:

- отдельный ART-документ;
- параллельное досье материала;
- отдельный итоговый контейнер;
- новый VIA для каждого редактора;
- копию VIA Template вместо рабочего VIA.

Pilot-документ не заменяет VIA.

VIA не заменяет Pilot-документ.

Если задача не требует VIA, Coach не открывает VIA только ради формального соблюдения процесса.

---

# 16. Фиксация результатов Initialization

Результаты Initialization рекомендуется сохранять.

Они могут использоваться как:

- свидетельство первоначального понимания роли;
- основание допуска к Pilot;
- материал для Validation;
- источник наблюдений;
- основание для сравнения версий роли;
- пример запуска следующих редакторов.

В папке Initialization уже может находиться исторический отчёт:

```text
Editors/Coach/Initialization/INIT-COACH-001-REPORT.md
```

Этот документ сохраняет результат первого запуска и не перезаписывается при последующих Initialization.

Новый отчёт создаётся отдельно только тогда, когда Mentor считает его необходимым.

В фиксацию Initialization могут входить:

1. использованное первое сообщение;
2. Initialization Report;
3. ответ Mentor;
4. уточнения Coach;
5. итоговый статус;
6. ссылка на последующий Pilot;
7. существенные наблюдения о понятности документации.

Обнаруженное наблюдение не переносится автоматически в Backlog.

Для этого должны существовать достаточное основание и отдельное решение.

---

# 17. Повторная Initialization

Повторная Initialization может потребоваться, если:

- создан новый постоянный рабочий диалог;
- существенно изменена Constitution;
- изменено каноническое определение роли;
- изменились полномочия или ограничения Coach;
- существенно обновлён Workflow;
- изменена архитектура VIA;
- появились новые нормативные документы;
- предыдущий Pilot выявил серьёзное непонимание роли;
- между документацией и фактической практикой возникло существенное расхождение.

Повторная Initialization может быть:

## Полной

Coach повторно проходит весь протокол и подготавливает новый Initialization Report.

## Сфокусированной

Coach изучает только изменённые документы и подготавливает отчёт о понимании конкретного блока изменений.

Формат повторной Initialization определяет Mentor.

Наличие обновлённого документа само по себе не означает, что полная Initialization обязательна.

---

# 18. Критерии успешного завершения

Initialization считается завершённой, если:

- Coach изучил обязательные документы;
- понял миссию In Profundo;
- сформулировал назначение Editorial Coach;
- обозначил границы полномочий;
- понял место роли в Editorial System;
- различает функции основных документов;
- описал действующий Workflow;
- понял функцию VIA;
- понял различие между Pilot и VIA;
- понял цикл развития роли;
- отделил действующие положения от гипотез;
- обозначил существенные неясности;
- получил обратную связь Mentor;
- устранил критические ошибки понимания;
- получил статус `Ready for Pilot`.

До выполнения этих условий практический Pilot не начинается.

---

# 19. Основной принцип

Editorial Coach не начинает работу только потому, что получил название роли и доступ к документации.

Сначала он должен понять:

- кому служит его работа;
- какую функцию выполняет роль;
- где проходят её границы;
- как принимаются решения;
- как устроен редакционный процесс;
- какую функцию выполняет VIA;
- как наблюдение может привести к развитию системы;
- почему изменение требует Validation;
- что в In Profundo должно сохраняться даже во время роста.

Initialization превращает запуск роли из технического подключения в осмысленное вхождение в Editorial System.
