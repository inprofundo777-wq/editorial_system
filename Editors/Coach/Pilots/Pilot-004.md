# Pilot-004 — Simplified VIA and Handoff Pilot

## Статус

**Planned / Ready to Launch after EXP-001 Portfolio Close**

Pilot-004 является следующим эксплуатационным экспериментом Editorial System после Pilot-003.

Он проверяет не выбор темы и не создание Content Portfolio.

Его входом является уже закрытый Content Portfolio, подготовленный в рамках:

```text
Development/Experiments/EXP-001-Content-Portfolio.md
```

Основная задача Pilot-004 — проверить, может ли производственный цикл статьи работать с минимальным участием Owner после передачи одной ссылки на закрытый Portfolio.

---

# 1. Граница Pilot-004

Pilot-004 начинается здесь:

```text
Closed Content Portfolio
→ Editorial Coach
```

и проходит через:

```text
Coach
→ VIA
→ Draft
→ Review
→ Revision
→ Final Check
→ Publication
→ Close
```

Выбор следующей темы уже завершён в Content Portfolio.

Coach не должен повторно открывать стратегический выбор материала без существенного основания.

---

# 2. Главная цель

Проверить, можно ли уменьшить административную работу Owner до нескольких простых действий:

1. передать ссылку;
2. перенести результат редактора в VIA;
3. изменить статус завершённого шага `0 → +`;
4. активировать следующий шаг `- → 0`.

Вся остальная логика должна находиться:

* в VIA;
* в документации роли;
* в задании соответствующего блока;
* в результате предыдущего этапа.

---

# 3. Вход Pilot-004

Editorial Coach получает:

```text
одну ссылку на закрытый Content Portfolio
```

Coach должен самостоятельно:

1. определить первую тему в активной Publication Queue;
2. прочитать Portfolio Package темы;
3. создать новый VIA;
4. сформировать достаточное Editorial / Draft Assignment;
5. подготовить VIA к передаче Longform Editor.

Если Coach не способен сделать это без дополнительного объяснения Owner, это фиксируется как Pilot Observation.

---

# 4. VIA

Pilot-004 продолжает принцип:

> **один материал — один рабочий VIA**

VIA остаётся единым рабочим документом развития конкретной статьи.

При этом Pilot-004 специально проверяет, можно ли уменьшить статусную и переходную бюрократию.

---

# 5. Минимальная система статусов

Используются только три значения:

| Статус | Значение                                                        |
| ------ | --------------------------------------------------------------- |
| `-`    | этап или шаг ещё не активирован                                 |
| `0`    | этап или шаг активен; соответствующий редактор может приступать |
| `+`    | этап или шаг завершён                                           |

Другие статусы не используются без доказанной необходимости.

Не вводить автоматически:

* Pending;
* Waiting;
* Ready;
* In Progress;
* Completed;
* Approved;
* Not Required;
* отдельные статусы каждого редактора;
* дополнительные административные состояния.

---

# 6. Рабочая таблица VIA

В начале VIA находится компактная таблица состояния.

Пример:

| Блок            | Шаг                     | Статус |
| --------------- | ----------------------- | :----: |
| **Formation**   | Portfolio → VIA         |    +   |
|                 | Draft Assignment        |    +   |
| **Draft**       | Longform Draft          |    0   |
| **Review**      | Literary Review         |    -   |
|                 | Theology Review         |    -   |
|                 | Reader Review           |    -   |
|                 | Strategy Review         |    -   |
|                 | SEO Review              |    -   |
|                 | Coach Integrated Review |    -   |
| **Revision**    | Longform Revision       |    -   |
| **Final Check** | Required Re-checks      |    -   |
| **Publication** | SEO Publication Package |    -   |
|                 | Visual                  |    -   |
|                 | Publication             |    -   |
| **Close**       | Notion Update           |    -   |
|                 | Pilot Observation       |    -   |

Таблица является оперативным интерфейсом.

Она не должна превращаться в подробный журнал переходов.

---

# 7. Formation

В Pilot-004 Formation уже не отвечает на вопрос:

> какую тему выбрать?

Это завершено в Portfolio.

Formation отвечает только на вопрос:

> **что необходимо определить, чтобы выбранная тема могла перейти в Draft?**

Coach:

* читает Portfolio Package;
* сохраняет уже принятый стратегический замысел;
* определяет конкретную задачу Longform;
* при необходимости уточняет исследовательские или богословские ограничения;
* формирует Draft Assignment;
* не повторяет полный Strategy / Reader / SEO review темы.

Formation должен быть значительно легче, чем в Pilot-003.

---

# 8. Coach → VIA contract

Coach самостоятельно создаёт VIA на основании Portfolio.

VIA должен содержать достаточный вход для Longform Editor:

* тему;
* центральный вопрос;
* место материала в серии или портфеле;
* существенный Reader context;
* существенный SEO context;
* связанные опубликованные материалы;
* ограничения;
* ожидаемый характер статьи;
* конкретный Draft Assignment.

Owner не должен вручную пересказывать Portfolio Longform Editor.

---

# 9. VIA → Longform contract

Longform Editor получает:

```text
одну ссылку на VIA
```

Если в таблице:

```text
Longform Draft | 0
```

Longform должен понять:

* что его этап активен;
* где находится вход;
* что необходимо создать;
* в каком формате вернуть результат.

Ожидаемый результат:

> цельный Markdown Draft, готовый к переносу в VIA.

Owner не должен заново объяснять Longform Editor задачу.

Если дополнительное объяснение понадобилось, фиксируется:

```text
Pilot Observation:
какой именно информации не хватило
```

---

# 10. Review

После Draft активируется Review.

Pilot-004 сохраняет принцип Independent Reviews.

Возможный состав:

* Literary;
* Theology;
* Reader;
* Strategy;
* SEO.

Конкретные роли могут быть сокращены, если их участие не требуется материалу.

Каждый Review должен иметь ясный Output Contract.

Минимально редактор должен понимать:

```text
INPUT
что читать

TASK
что именно проверить

BOUNDARY
что не делать

OUTPUT
что вернуть

FORMAT
Markdown ready for VIA
```

Pilot-004 специально наблюдает, достаточно ли документации редактора и VIA, чтобы не объяснять этот контракт вручную в каждом цикле.

---

# 11. Coach Integrated Review

После Independent Reviews Coach:

* объединяет повторяющиеся замечания;
* сохраняет важные различия;
* отделяет обязательные исправления от рекомендаций;
* отмечает реальные конфликты;
* формирует единый Revision Package.

Longform Revision не должен перечитывать несколько несведённых Reviews как замену интеграции Coach.

---

# 12. Revision

Longform получает активный статус:

```text
Longform Revision | 0
```

и работает по Integrated Review.

Результат:

> новая цельная версия статьи, а не перечень локальных исправлений.

После переноса Revision в VIA статус становится `+`.

---

# 13. Final Check

Final Check используется только для необходимых локальных проверок.

Он не должен превращаться во второй полный Review.

Coach определяет, какие re-check действительно необходимы.

Если повторная проверка роли не нужна, соответствующий шаг может отсутствовать в конкретном VIA.

---

# 14. Publication

Publication включает только необходимые действия конкретного материала.

Потенциально:

* Final Text;
* SEO Publication Package;
* Visual;
* Blogger / platform preparation;
* Publication;
* published-page check.

Pilot-004 не обязан включать Telegram и Facebook внутрь VIA, если их сохранение там не снижает нагрузку Owner.

Distribution может оставаться отдельным рабочим процессом до последующего решения.

---

# 15. VIA → Notion Close Package

После публикации должен быть сформирован минимальный пакет данных для обратной передачи в Notion.

Окончательный состав Pilot-004 не утверждает.

Минимально проверить необходимость:

* Published;
* финальное название;
* дата публикации;
* URL;
* VIA ID;
* GitHub reference;
* рубрика;
* серия;
* состояния человека;
* основной поисковый вопрос;
* новые темы или продолжения, обнаруженные в процессе.

Pilot должен показать, какой объём возврата оправдан при ручной работе.

---

# 16. Работа Owner

Целевое административное действие Owner:

```text
получить результат
→ вставить в VIA
→ 0 заменить на +
→ следующий - заменить на 0
→ передать ссылку
```

Owner не должен:

* формировать повторное ТЗ для каждого редактора;
* пересказывать содержание предыдущего этапа;
* объяснять ожидаемый формат результата;
* выбирать следующую тему внутри VIA;
* поддерживать отдельный журнал статусов;
* вручную синхронизировать несколько параллельных рабочих документов.

Если одно из этих действий оказывается необходимым, это считается важным наблюдением Pilot.

---

# 17. Проверяемые гипотезы

## H1 — Portfolio → Coach

Coach способен начать производство по одной ссылке на закрытый Portfolio.

## H2 — Coach → VIA

Coach способен самостоятельно превратить Portfolio Package в качественный VIA и Draft Assignment.

## H3 — VIA → Editor

Редактор способен начать работу по одной ссылке на VIA и статусу `0`.

## H4 — Minimal status system

Система `- / 0 / +` достаточна для управления производственным циклом.

## H5 — Output Contracts

Редакторы способны возвращать предсказуемые результаты без дополнительных инструкций Owner.

## H6 — Stage Handoffs

Результат одного крупного блока содержит достаточный пакет для следующего.

## H7 — Reduced Owner Load

Административная нагрузка Owner заметно ниже Pilot-003.

---

# 18. Что фиксировать как Observation

Особенно фиксировать:

* сколько раз Owner пришлось дополнительно объяснять задачу;
* какому редактору;
* чего именно ему не хватило;
* был ли понятен статус `0`;
* был ли VIA достаточным входом;
* где потребовалось читать чрезмерно большой объём предыдущего материала;
* где возникло дублирование;
* где Coach пришлось вручную переводить контекст между ролями;
* какие статусы кроме `- / 0 / +` реально понадобились;
* сколько действий Owner потребовалось между этапами;
* какие шаги можно было бы объединить в будущую Stage College.

---

# 19. Правило экспериментального сбоя

Если редактор не понял задачу, процесс не останавливается ради чистоты эксперимента.

Owner или Coach может дать необходимое уточнение.

Но одновременно обязательно фиксируется:

```text
что пришлось объяснить
почему VIA/роль не дали этого автоматически
какого элемента handoff contract не хватило
```

Не исправлять проблему незаметно.

Она является данными Pilot-004.

---

# 20. Связь с будущей Stage College Architecture

Pilot-004 не внедряет Stage Colleges.

Но он должен собирать данные для будущего вопроса:

> Какие задачи естественно относятся к одному крупному этапу и могут быть скрыты внутри одной коллегии?

Особенно наблюдать:

* Formation;
* Review;
* Publication;
* Close.

Если несколько специализированных редакторов регулярно требуют одного и того же общего входа и выдают результаты, которые затем интегрируются в один общий пакет, это является потенциальным основанием будущей Stage College.

---

# 21. Критерии успешности

Pilot-004 считается успешным, если:

* Coach запускает VIA по закрытому Portfolio без повторного выбора темы;
* Longform начинает Draft по одной ссылке на VIA;
* большинство редакторов понимают задачу без дополнительных объяснений Owner;
* `- / 0 / +` достаточно для фактического управления процессом;
* VIA остаётся читаемым и не обрастает административными слоями;
* handoff между крупными блоками становится яснее;
* Owner преимущественно выполняет только перенос результата и смену статуса;
* статья успешно проходит производственный цикл;
* Observation даёт конкретные данные для Editor Renewal и дальнейшей архитектуры.

---

# 22. Что Pilot-004 не утверждает

Pilot-004 не утверждает автоматически:

* окончательный VIA Template;
* окончательную Stage College Architecture;
* окончательные редакторские Modes;
* постоянный состав Review;
* постоянный набор статусов;
* автоматизацию передачи;
* окончательную роль Notion;
* окончательный Close Protocol.

Все эти решения принимаются только после накопления достаточной практики.
