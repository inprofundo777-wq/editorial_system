# 1. Назначение

Настоящий Pilot проверяет работу обновлённого Editorial Coach в реальном редакционном цикле In Profundo.

Pilot должен установить:

- понятна ли роль Editorial Coach без дополнительного восстановления прежнего контекста;
- применимо ли каноническое определение роли;
- соблюдаются ли границы полномочий;
- работает ли обновлённый Workflow;
- используется ли VIA как единый источник состояния редакционного цикла;
- достаточно ли одной активной ссылки для передачи работы;
- правильно ли Coach определяет текущий и следующий этап;
- работают ли этапы `Close` и `Observe`;
- различаются ли Observation, Pattern, Backlog и Development;
- достаточно ли Checklist для завершения работы;
- не создаёт ли обновлённая документация неоправданной административной нагрузки.

Pilot одновременно является практической Validation для:

```text
DEV-001–DEV-004
```

---

# 2. Границы Pilot

Pilot проверяет работу роли в реальной задаче.

Он не предназначен для:

- искусственной демонстрации всех возможностей Coach;
- создания системных проблем ради проверки процесса;
- автоматического продвижения наблюдений в Backlog;
- автоматического создания новых DEV-записей;
- изменения документации во время самого рабочего цикла;
- повторного утверждения уже принятых решений `DEV-001–DEV-004`;
- проверки литературного качества материала вместо специализированных редакторов.

Pilot не должен усложнять реальный редакционный цикл только ради полноты отчёта.

Если какой-либо этап не требуется по масштабу задачи, Coach должен прямо зафиксировать причину его неприменения.

# 3. Связь Pilot и VIA

Pilot и VIA выполняют разные функции.

```text
Pilot-002
        ↓
проверяет работу Editorial Coach

Связанный VIA
        ↓
содержит состояние и результаты редакционного цикла материала
```

Pilot-002 фиксирует:

- цель проверки;
- критерии Validation;
- наблюдения за работой Coach;
- системные выводы;
- результат Validation;
- решения по `DEV-001–DEV-004`.

Связанный VIA фиксирует:

- материал;
- редакционное техническое задание;
- текущий этап;
- работу редакторов;
- редакции текста;
- решения;
- публикацию;
- закрытие конкретного цикла.

Pilot не заменяет VIA.

VIA не заменяет Pilot.

Все участники работают по одной активной ссылке на связанный VIA.

# 7. Роли

## 7.1. Владелец проекта / Mentor

Владелец проекта:

- выбирает реальную задачу;
- утверждает запуск Pilot;
- создаёт связанный VIA в GitHub;
- передаёт одну активную ссылку;
- принимает авторские, богословские и стратегические решения;
- оценивает работу Coach;
- утверждает результат Validation;
- принимает решение по статусам `DEV-001–DEV-004`.

## 7.2. Editorial Coach

Coach:

- использует README как входную точку;
- изучает актуальное состояние задачи;
- определяет масштаб цикла;
- формирует достаточный редакционный маршрут;
- подготавливает VIA;
- подключает только необходимые роли;
- передаёт участникам конкретные задания;
- не подменяет специализированных редакторов;
- интегрирует результаты;
- представляет решения владельцу проекта;
- закрывает редакционный цикл;
- проводит Observe;
- отделяет результаты материала от наблюдений о системе;
- подготавливает Pilot Report.

## 7.3. Специализированные редакторы

Подключённые редакторы:

- работают в пределах собственных мандатов;
- получают одну действующую ссылку на VIA;
- читают актуальное состояние VIA;
- выполняют конкретно сформулированную задачу;
- не создают параллельный VIA;
- не используют шаблон вместо действующего VIA;
- передают результат для внесения в установленный раздел VIA.

# 8. Рабочий процесс Pilot

Pilot проводится через действующий Editorial Coach Workflow.

## 8.1. Workflow Stage 10 — Understand

Coach должен определить:

- что именно требуется владельцу проекта;
- какой практический результат должен завершить цикл;
- какие материалы уже существуют;
- какие ограничения необходимо сохранить;
- относится ли задача к существующей серии;
- какие документы должны быть изучены;
- требуется ли участие специализированных редакторов.

### Проверяемый результат

Задача понята без неоправданного расширения.

---

## 8.2. Workflow Stage 20 — Frame

Coach определяет масштаб работы.

Он должен установить:

- является ли задача локальной или требует полного редакционного цикла;
- какие части задачи относятся к материалу;
- какие возможные вопросы относятся к Editorial System;
- где проходит граница между текущей работой и развитием системы;
- какие решения остаются за владельцем проекта.

### Проверяемый результат

Масштаб задачи определён без перевода единичной трудности на системный уровень.

---

## 8.3. Workflow Stage 30 — Plan

Coach формирует достаточный редакционный маршрут.

План должен определить:

- необходимые этапы;
- требуемые роли;
- последовательность участников;
- ожидаемый результат каждого этапа;
- точки решения владельца проекта;
- способ фиксации результатов в VIA;
- критерий завершения цикла.

### Проверяемый результат

План достаточен для работы и не содержит лишних участников или формальных этапов.

---

## 8.4. Workflow Stage 40 — Open or Read VIA

Coach подготавливает новый VIA либо читает уже созданный VIA.

Перед началом работы Coach должен проверить:

- актуальность шаблона;
- актуальные документы и версии;
- паспорт VIA;
- текущий этап;
- следующий этап;
- статус основного текста;
- связанные документы;
- ожидаемый результат следующего участника.

### Проверяемый результат

VIA позволяет восстановить состояние цикла без обращения к памяти или параллельным рабочим документам.

---

## 8.5. Workflow Stage 50 — Coordinate

Coach организует работу необходимых редакторов.

Для каждого участника должно быть ясно:

- почему он подключён;
- что именно требуется проверить;
- какую редакцию он анализирует;
- какой результат ожидается;
- где результат должен быть зафиксирован;
- какое действие следует после его работы.

### Проверяемый результат

Редакторы понимают задачу без избыточных ручных пояснений и работают через одну активную ссылку.

---

## 8.6. Workflow Stage 60 — Integrate

Coach рассматривает результаты редакторов и формирует интегрированную картину.

Он должен:

- учесть все существенные заключения;
- объединить совпадающие выводы;
- сохранить значимые расхождения;
- отличить обязательные изменения от рекомендаций;
- не присваивать себе решение специализированного редактора;
- не присваивать себе окончательное решение владельца проекта;
- зафиксировать открытые вопросы.

### Проверяемый результат

Интеграция сохраняет независимость редакторов и предоставляет владельцу проекта ясную основу для решения.

---

## 8.7. Workflow Stage 70 — Present

Coach представляет владельцу проекта результат в форме, соответствующей задаче.

Представление должно различать:

- факты;
- редакторские наблюдения;
- гипотезы;
- рекомендации;
- обязательные изменения;
- решения владельца проекта;
- следующий практический шаг.

### Проверяемый результат

Владелец проекта понимает, что уже установлено, что предлагается и какое решение требуется.

---

## 8.8. Workflow Stage 80 — Close

После завершения практической работы Coach проверяет:

- завершены ли предусмотренные этапы;
- внесены ли результаты редакторов;
- зафиксированы ли решения владельца проекта;
- отражён ли актуальный статус текста;
- указан ли результат цикла;
- закрыты ли препятствующие вопросы;
- указан ли статус публикации или следующего производственного этапа;
- установлен ли явный маркер закрытия VIA.

### Проверяемый результат

Редакционный цикл может быть формально признан завершённым.

---

## 8.9. Workflow Stage 90 — Observe

После закрытия задачи Coach оценивает процесс.

Он должен определить:

- что сработало хорошо;
- что оказалось лишним;
- где требовались дополнительные пояснения;
- какие этапы были неясны;
- какие документы помогли;
- какие документы оказались недостаточными;
- появились ли значимые наблюдения о системе;
- является ли каждое наблюдение единичным случаем или возможным паттерном.

### Проверяемый результат

Наблюдения отделены от результата материала и не превращены автоматически в системные изменения.

# 12. Проверка жизненного цикла развития роли

Pilot должен проверить применимость пути:

```text
Practice
        ↓
Observation
        ↓
Pattern
        ↓
Backlog
        ↓
Backlog Review
        ↓
Development
        ↓
Documentation Update
        ↓
Validation
```

Проверка не требует искусственно проводить каждое наблюдение через весь цикл.

Успешным результатом также считается обоснованное решение:

- оставить вывод единичным наблюдением;
- продолжить наблюдение;
- не создавать запись Backlog;
- не передавать вопрос в Development.

Наблюдение может перейти в Backlog только при наличии достаточного основания.

Передача из Backlog в Development требует отдельного решения владельца проекта.

---

# 13. Проверка Checklist

Перед закрытием цикла Coach применяет:

```text
Editors/Coach/Checklist.md
```

Необходимо установить:

- охватывает ли Checklist критические границы роли;
- помогает ли он проверить VIA;
- помогает ли он завершить редакционный цикл;
- различает ли текущий результат и системное наблюдение;
- не повторяет ли он весь Workflow;
- не создаёт ли лишнюю формальную нагрузку;
- позволяет ли обнаружить незавершённые действия.

# 14. System Observations

Наблюдения о работе Editorial System фиксируются отдельно от результата редакционного проекта.

Каждое наблюдение оформляется по структуре:

```md
## OBS-000 — Название наблюдения

**Контекст**  
На каком этапе и в какой ситуации возникло наблюдение.

**Факт**  
Что фактически произошло.

**Предварительная интерпретация**  
Почему это может быть значимо.

**Классификация**  
Observation | Possible Pattern | Existing Pattern

**Затронутые документы**  
Какие документы или процессы могут быть связаны с наблюдением.

**Рекомендуемое действие**  
Continue Observation | Backlog Candidate | No Action

**Решение Mentor**  
Заполняется владельцем проекта.
```

Наличие наблюдения не означает автоматического создания новой нормы.

Если значимых наблюдений нет, прямо фиксируется:

```text
Новых системных наблюдений, требующих фиксации, не обнаружено.
```

# 16. Общие критерии успешности

Pilot считается успешным, если:

- реальный редакционный результат достигнут;
- Coach правильно понял задачу;
- масштаб работы оказался достаточным;
- подключены только необходимые роли;
- VIA использовался как единый источник состояния;
- участники работали по одной активной ссылке;
- текущий и следующий этапы были понятны;
- результаты редакторов были интегрированы;
- решения владельца проекта были отделены от рекомендаций;
- цикл был формально закрыт;
- этап Observe был проведён;
- наблюдения не были автоматически превращены в изменения;
- Checklist оказался практически применимым;
- документация Coach не потребовала постоянного устного восстановления;
- процесс не создал неоправданной административной нагрузки.

Успех Pilot не требует отсутствия любых замечаний.

Он требует, чтобы выявленные замечания:

- были конкретными;
- не разрушали основной Workflow;
- могли быть исправлены без создания параллельной архитектуры;
- были правильно классифицированы.
