# Pilot-003 — Master Editorial Assignment to Coach

## Pilot of Simplified Editorial Production Model

### Статус документа

**Master Editorial Assignment**

Этот документ является исходным редакционным заданием **Master Editor → Editorial Coach** для подготовки и проведения `Pilot-003`.

Он определяет:

* зачем проводится Pilot-003;
* какую модель он проверяет;
* стратегические границы пилота;
* обязательные элементы маршрута;
* роли и зоны ответственности;
* критерии успешности;
* границы полномочий Coach;
* ожидаемый результат пилота.

Coach принимает эту рамку как исходную.

Coach имеет право проектировать **операционное проведение пилота внутри заданной рамки**, но не должен самостоятельно переопределять его стратегическую цель, предмет проверки или редакционную архитектуру.

---

# 1. Назначение Pilot-003

Pilot-003 является следующим эксплуатационным экспериментом Editorial System In Profundo после Pilot-001 и Pilot-002.

Его задача — проверить в работе не отдельную роль Coach, а **обновлённую производственную модель Editorial System** на одном реальном longform-материале.

Pilot-003 должен проверить:

* новую упрощённую структуру VIA;
* семиблочную производственную модель;
* отдельный блок Observation;
* расширенный состав редакторов;
* короткие задания с заранее обозначенным ожидаемым результатом;
* Independent Reviews;
* Coach Integrated Review;
* цельную Revision;
* локальный Final Check;
* более ясные передачи работы между редакторами;
* снижение ручной и административной нагрузки Owner.

Дополнительной задачей Pilot-003 становится наблюдение за **контрактами передачи между ролями**, прежде всего:

```text
Master Editor
→ Editorial Coach
→ специализированные редакторы
→ Coach Integration
→ Revision
→ Master / Owner
```

Pilot-003 не является автоматическим утверждением новой архитектуры.

Полученные результаты должны использоваться как практические данные для последующей ревизии Editorial System и Editor Renewal.

# 2. Исторический контекст

Перед запуском Pilot-003 необходимо учитывать опыт двух предыдущих пилотов.

## Pilot-001

Pilot-001 стал первым практическим испытанием Coach и VIA как способа проведения материала через редакционный процесс.

Его опыт используется как историческая точка отсчёта.

## Pilot-002

Pilot-002 выявил как сильные стороны системы, так и существенную ручную нагрузку Owner.

Его итоговый статус сохраняется:

```text
Closed — Successful with Required Revisions
```

Особенно учитывать наблюдения Pilot-002, связанные с:

* количеством ручных передач;
* дублированием информации;
* избыточными статусами;
* необходимостью цельных Markdown-результатов;
* отсутствием ясных контрактов передачи между ролями;
* административной нагрузкой на Owner.

Pilot-003 не является продолжением или повторным открытием Pilot-002.

# 4. Проверяемая производственная модель

Pilot-003 использует семь последовательных производственных блоков:

```text
1. Formation
2. Draft
3. Review
4. Revision
5. Final Check
6. Publication
7. Distribution
```

После основного производственного цикла проводится:

```text
8. Observation
```

`Observation` не является восьмым производственным этапом материала.

Его задача — отделить:

```text
результат материала
```

от

```text
наблюдений о работе Editorial System
```

---

## Review

Внутри блока `Review` обязательно различаются:

```text
Independent Reviews
→ Coach Integrated Review
```

Independent Reviews сохраняют независимость редакторских компетенций.

Coach не должен заранее сводить редакторов к общему мнению.

После получения независимых Reviews Coach:

* выявляет повторяющиеся замечания;
* устраняет дублирование;
* различает обязательные исправления и рекомендации;
* отмечает реальные конфликты между Reviews;
* формирует одно ясное направление Revision.

---

## Publication

Внутри `Publication` могут находиться:

* Final Text;
* SEO Package;
* Visual;
* Publication Data;
* Published Page Check;
* Article Cycle Close.

Эти элементы не становятся автоматически отдельными производственными блоками.

# 5. Связанный VIA

Pilot-003 использует:

```text
VIA/2026/VIA-2026-014.md
```

Единственным действующим основанием структуры VIA является:

```text
Templates/VIA-YYYY-NNN.md
```

VIA должен оставаться **единым читаемым рабочим документом развития материала**.

Главный принцип:

> один материал — один рабочий VIA.

Не создавать параллельные документы для отдельных этапов, если этого не требует реальная работа.

Не возвращать в VIA административные конструкции старых версий только потому, что они использовались ранее.

Без практической необходимости не добавлять:

* подробную таблицу всех переходов;
* повторяющиеся статусы;
* отдельный статус каждой роли;
* обязательные записи `Not Required`;
* длинную историю изменений;
* реестр нормативных документов;
* повторяющиеся Owner Decisions;
* отдельный документ на каждый производственный этап;
* формальную систему A / B / C;
* новые постоянные чек-листы;
* новую нормативную архитектуру.

# 6. Контракт Master Editor → Coach

Это ключевая граница Pilot-003.

## Master Editor определяет

Master Editor задаёт стратегическую рамку Pilot-003:

* назначение пилота;
* предмет проверки;
* производственную модель;
* ключевые ограничения;
* состав рассматриваемых редакционных компетенций;
* критерии успешности;
* место пилота в развитии Editorial System;
* редакционную задачу материала после её утверждения Owner;
* существенные условия, которые Coach не должен изменять самостоятельно.

Master Editor не обязан проектировать каждую рабочую передачу внутри Pilot.

---

## Editorial Coach определяет

Получив Master Editorial Assignment, Coach отвечает за операционную реализацию.

Coach вправе:

* определить практическую последовательность работы внутри утверждённых блоков;
* определить достаточный объём Formation;
* подготовить короткие задания редакторам;
* определить, когда конкретная компетенция действительно необходима;
* организовать Independent Reviews;
* интегрировать Reviews;
* направить Revision;
* назначить необходимые локальные re-check;
* вести VIA;
* фиксировать Pilot Observations;
* предлагать улучшения системы как Observation.

---

## Coach не должен самостоятельно

* менять стратегическую цель Pilot-003;
* менять предмет проверки;
* заменять утверждённую производственную модель другой;
* создавать новую нормативную архитектуру;
* переопределять роль Pilot-003;
* менять редакционную цель материала;
* выбирать материал вместо Owner;
* превращать временную пилотную практику в постоянное правило;
* изменять документы Editorial System;
* создавать Accepted Decision;
* переписывать роли редакторов;
* подменять Master Editor;
* принимать фундаментальные содержательные решения вместо Owner.

Если Coach считает изменение стратегической рамки необходимым, он должен оформить:

```text
Coach Observation / Recommendation
```

и вернуть вопрос Master Editor / Owner.

# 7. Состав Pilot-003

Pilot-003 намеренно использует расширенный набор компетенций.

Цель — не доказать необходимость всех ролей, а получить данные о том:

* какие входы реально полезны;
* где возникает дублирование;
* какие роли нужны постоянно;
* какие должны подключаться селективно.

## Formation

Предварительно рассматриваются:

* Owner;
* Strategy Editor;
* SEO Editor;
* Reader Board;
* Editorial Coach.

## Draft

* Longform Editor.

## Review

Independent Reviews:

* Literary Editor;
* Theology Editor;
* Reader Board;
* Strategy Editor;
* SEO Editor.

Integration:

* Editorial Coach.

## Revision

* Longform Editor.

## Final Check

Только редакторы, чьи существенные замечания требуют проверки:

* необходимые специализированные редакторы;
* Editorial Coach;
* Owner — при наличии реальной точки решения.

## Publication

По необходимости:

* Longform Editor;
* SEO Editor;
* Visual Editor;
* Editorial Coach;
* Owner.

## Distribution

Подключаются только компетенции, необходимые для конкретных платформенных материалов.

Расширенный состав не означает обязательного повторного подключения каждой роли на каждом блоке.

# 8. Принцип работы редакторов

Каждая редакторская передача должна быть короткой и предметной.

Coach передаёт редактору:

1. текущий блок;
2. ссылку на актуальный VIA;
3. конкретную задачу;
4. ожидаемый результат;
5. ограничения;
6. точный раздел VIA, для которого готовится результат.

Редактор возвращает:

> цельный Markdown-результат, пригодный для непосредственного переноса в VIA.

Не запрашивать:

* пересказ всего материала;
* формальный отчёт ради отчёта;
* повтор работы другой роли;
* полный Review, если требуется локальный re-check;
* разработку Editorial System;
* создание параллельного VIA;
* административную информацию, которая не влияет на материал.

# 9. Особая задача Pilot-003 — наблюдение за ролями

Pilot-003 проходит одновременно с подготовкой будущего `Editor Renewal`.

Поэтому пилот должен дать реальные наблюдения о работе редакторов.

Для каждой подключённой компетенции желательно фиксировать только практически значимые наблюдения:

* какую ценность роль внесла;
* на каком этапе она была наиболее полезна;
* что дублировала;
* чего ей не хватало;
* какие границы роли оказались неясными;
* что произошло при передаче работы следующему редактору.

Pilot-003 не переписывает документацию редакторов.

Он поставляет **эмпирический материал для их будущего Review**.

# 10. Ключевые вопросы Pilot-003

Pilot должен собрать практические данные по следующим вопросам.

### Производственная модель

1. Достаточны ли семь производственных блоков?
2. Помогает ли отдельный `Observation`, не усложняя цикл?
3. Достаточен ли новый VIA для восстановления состояния материала?
4. Можно ли закрывать основной цикл статьи независимо от полного завершения Distribution?

### Owner workload

5. Снизилось ли количество ручных передач?
6. Приходится ли Owner вручную собирать и форматировать ответы редакторов?
7. Где Owner всё ещё становится обязательным техническим посредником?

### Редакторские передачи

8. Работают ли короткие задания с заранее обозначенным результатом?
9. Понимает ли следующий редактор, что именно получает от предыдущего этапа?
10. Какие контракты передачи необходимо будет сформализовать позже?

### Formation

11. Какие ранние редакторские входы действительно влияют на Draft?
12. Какие Formation-входы оказываются избыточными?

### Review

13. Где возникает дублирование Independent Reviews?
14. Возникают ли реальные содержательные противоречия?
15. Способен ли Coach превратить независимые Reviews в одно ясное направление Revision?

### Revision / Final Check

16. Получается ли Revision цельной, а не механической?
17. Достаточен ли локальный Final Check?

### Роли

18. Какие роли выглядят постоянными?
19. Какие роли должны подключаться селективно?
20. Какие редакционные функции отсутствуют в текущей системе?
21. Какие границы между ролями требуют пересмотра?

### Система

22. Какие элементы нового VIA требуют уточнения?
23. Какие наблюдения должны перейти в Editor Renewal?
24. Какие изменения следует проверить ещё на Pilot-004 / Pilot-005 прежде, чем документировать постоянно?

---

# 11. Ограничения Pilot-003

Во время пилота:

* не изменять Editorial System;
* не создавать Accepted Decision;
* не переписывать документы редакторов;
* не создавать новые постоянные роли только на основании одного случая;
* не создавать новую документацию производственных блоков;
* не вводить формальную систему A / B / C;
* не создавать автоматизацию;
* не расширять Pilot за пределы одного реального longform-материала;
* не исправлять автоматически противоречия между фундаментальными документами;
* не заполнять VIA вымышленными данными;
* не превращать Observation в параллельный процесс;
* не увеличивать административную нагрузку Owner ради полноты документации.

Главный принцип:

> Pilot-003 существует для проверки работы системы, а не для строительства новой системы внутри самого Pilot.

# 14. Условие фактического запуска

Pilot-003 считается фактически запущенным, когда одновременно выполнены следующие условия:

* существует `Pilot-003.md`;
* существует актуальный `VIA-2026-014.md`;
* Owner определил материал;
* исходная идея внесена в VIA;
* Coach определил достаточный маршрут Formation;

После этого:

```text

→ Draft

→ Revision
→ Final Check
→ Publication
→ Distribution
→ Observation
```

# 15. Первое действие Coach после принятия этого задания

Coach не должен заново проектировать Pilot-003 с чистого листа.

Необходимо:

### A. Сопоставить

Сравнить уже подготовленные:

* `Pilot-003.md`;
* `VIA-2026-014.md`;
* текущую работу в памяти Coach;

с настоящим Master Editorial Assignment.

### B. Определить расхождения

Выделить только существенные расхождения:

* стратегическая цель;
* предмет проверки;
* роли;
* производственные блоки;
* границы Coach;
* задания редакторам;
* структура Formation;
* критерии успешности.

Не проводить косметическое сравнение.

### C. Скорректировать

Если существенные расхождения существуют:

* обновить `Pilot-003.md` крупными блоками;
* скорректировать только необходимые части `VIA-2026-014`;
* не откатывать уже полезную работу;
* не создавать Pilot заново без необходимости.

### D. Вернуть Owner один стартовый пакет

После корректировки Coach должен вернуть:

1. краткое подтверждение принятия Master Editorial Assignment;
2. перечень существенных изменений Pilot;
3. актуальный `Pilot-003.md`;
4. актуальный блок `Formation` VIA;
5. следующий конкретный шаг процесса.

После этого Pilot-003 продолжается уже в рамках уточнённого контракта:

```text
Master Editor
→ Coach
→ Editors
→ Coach Integration
→ Revision
→ Master / Owner
```

# 16. Критерий успешности Master → Coach handoff

Отдельно в Pilot-003 наблюдается качество первой передачи:

```text
Master Editor → Editorial Coach
```

Передача считается успешной, если:

* Coach понимает, что проверяет Pilot;
* Coach понимает стратегические ограничения;
* Coach не вынужден заново проектировать цель Pilot;
* Coach имеет достаточную свободу для организации процесса;
* Master не управляет каждым техническим шагом;
* Owner не вынужден вручную устранять разницу между пониманием Master и Coach;
* операционный Pilot сохраняет исходную стратегическую задачу.

Результат этого наблюдения должен войти в итоговый `Observation` Pilot-003.

# 17. Ожидаемый итог

Pilot-003 должен дать одновременно два результата.

## Результат материала

Один реальный longform-материал проходит полный производственный цикл до публикации и последующего Distribution.

## Результат системы
