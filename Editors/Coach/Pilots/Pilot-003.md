# Запуск Pilot-003 — Pilot of Simplified Editorial Production Model

Приступи к подготовке и запуску третьего пилота Editorial System In Profundo.

Pilot‑003 должен проверить в реальной работе:

- новую упрощённую структуру VIA;
- семиблочную производственную модель;
- отдельный блок Observation;
- работу расширенного состава редакторов;
- короткие задания с заранее обозначенным ожидаемым результатом;
- Independent Reviews;
- Coach Integration;
- цельную Revision;
- локальный Final Check;
- снижение ручной и административной нагрузки Owner.

## 2. Статус Pilot-003

Pilot‑003 является:

- новым самостоятельным пилотом;
- первым из трёх материалов временной эксплуатационной проверки;
- проверкой производственной модели Editorial System, а не повторной Validation только роли Coach;
- рабочим пилотом, не изменяющим нормативную документацию автоматически.

Pilot‑003 не является продолжением или повторным открытием Pilot‑002.

Pilot‑002 сохраняет статус:

```text
Closed — Successful with Required Revisions
```

## 3. Проверяемая модель

В Pilot‑003 используется семь последовательных производственных блоков:

```text
1. Formation
2. Draft
3. Review
4. Revision
5. Final Check
6. Publication
7. Distribution
```

После производственного цикла проводится отдельный блок:

```text
8. Observation
```

Внутри блока `Review` различаются две фазы:

```text
Independent Reviews
→ Coach Integrated Review
```

Они не считаются двумя самостоятельными производственными блоками.

Внутри блока `Publication` могут находиться:

- Final Text;
- SEO Package;
- Visual;
- Publication Data;
- Published Page Check;
- Article Cycle Close.

Они не превращаются автоматически в самостоятельные производственные блоки.

## 4. Связанный VIA

Для Pilot‑003 должен использоваться:

```text
VIA/2026/VIA-2026-014.md
```

Основанием для его структуры является исключительно актуальный файл:

```text
Templates/VIA-YYYY-NNN.md
```

VIA должен оставаться единым читаемым документом развития материала.

Не возвращай в новый VIA административные конструкции старого шаблона, если они отсутствуют в актуальном Template.

Не добавляй без практической необходимости:

- подробную таблицу всех переходов;
- повторяющиеся статусы;
- отдельный статус каждой роли;
- обязательные записи `Not Required`;
- длинную историю изменений;
- реестр нормативных документов;
- повторяющиеся Owner Decisions;
- отдельный документ на каждый этап;
- формальную систему уровней A / B / C;
- новые постоянные чек-листы;
- новую нормативную архитектуру.

## 5. Состав Pilot-003

На Pilot‑003 используется расширенный состав редакторов.

Предварительно рассматриваются следующие подключения.

### Formation

- Owner;
- Strategy Editor;
- SEO Editor;
- Reader Board;
- Editorial Coach.

### Draft

- Longform Editor.

### Review

- Literary Editor;
- Theology Editor;
- Reader Board;
- Strategy Editor;
- SEO Editor;
- Editorial Coach — Integration.

### Revision

- Longform Editor.

### Final Check

- только редакторы, чьи существенные замечания требуют проверки;
- Editorial Coach;
- Owner.

### Publication

- Longform Editor;
- SEO Editor;
- Visual Editor;
- Editorial Coach;
- Owner — только в необходимых точках решения.

### Distribution

- редакторы и исполнители, необходимые для подготовки конкретных платформенных материалов.

Расширенный состав является пилотным.

Он не означает, что все перечисленные роли должны выполнять одинаковый объём работы или обязательно подключаться повторно на каждом этапе.

## 6. Принцип задания редакторам

Каждому подключённому редактору Coach должен передавать короткое задание, включающее:

1. название текущего блока;
2. ссылку на актуальный VIA;
3. конкретную задачу редактора;
4. ожидаемый результат;
5. необходимые ограничения;
6. точный раздел VIA, для которого готовится результат.

Редакторы должны возвращать цельный результат в формате Markdown, пригодный для непосредственного переноса в VIA.

Не запрашивай у редактора:

- пересказ всего материала;
- формальный отчёт ради отчёта;
- повторение работы другой роли;
- полный Review, если требуется локальная проверка;
- изменение Editorial System;
- создание параллельного VIA.

## 7. Роль Coach

В Pilot‑003 Coach должен:

- удерживать целостность маршрута;
- не подменять специализированных редакторов;
- не писать статью вместо Longform Editor;
- не принимать содержательные решения вместо Owner;
- формировать короткие задания;
- обозначать ожидаемый результат каждой передачи;
- интегрировать Independent Reviews;
- устранять дублирование рекомендаций;
- выделять обязательные изменения, рекомендации и точки решения Owner;
- направлять цельную Revision;
- назначать только необходимые локальные re-check;
- не создавать лишних статусных сообщений;
- обновлять рабочую модель крупными содержательными блоками;
- отделять результат материала от Observation о системе.

## 8. Что должен проверить Pilot-003

Pilot должен собрать практические данные по следующим вопросам:

1. Достаточны ли семь производственных блоков?
2. Помогает ли отдельный `Observation`, не усложняя производственный цикл?
3. Достаточен ли новый VIA для восстановления состояния материала?
4. Не приходится ли Owner вручную собирать и форматировать результаты редакторов?
5. Работают ли короткие задания и заранее обозначенный ожидаемый результат?
6. Какие ранние входы в Formation действительно влияют на Draft?
7. Где возникает дублирование между редакторами?
8. Способен ли Coach преобразовать независимые Reviews в одно ясное направление Revision?
9. Получается ли Revision цельной, а не механической?
10. Достаточен ли локальный Final Check?
11. Можно ли закрыть основной цикл статьи независимо от полного завершения Distribution?
12. Какие роли после трёх материалов должны стать постоянными, а какие селективными?
13. Какие элементы нового VIA требуют уточнения?
14. Насколько новая модель уменьшает ручную нагрузку Owner по сравнению с Pilot‑002?

## 9. Ограничения

Во время запуска Pilot‑003:

- не изменяй Editorial System;
- не создавай Accepted Decision;
- не переписывай документы редакторов;
- не создавай новую документацию блоков;
- не вводи формальную систему A / B / C;
- не создавай автоматизацию;
- не расширяй пилот за пределы одного реального longform-материала;
- не исправляй автоматически противоречия между документами;
- не переходи сразу к Draft до завершения Formation;
- не выбирай материал вместо Owner;
- не заполняй содержательные разделы VIA вымышленными данными.

Если обнаружишь несогласованность между актуальным VIA Template и другими документами, зафиксируй её кратко как Pilot Observation, но продолжай работу по актуальному VIA Template, если противоречие не делает запуск невозможным.

## 10. Первое действие

Сейчас не проводи весь редакционный цикл.

Выполни только подготовку запуска и начало блока `Formation`.

Подготовь следующие результаты.

### A. Launch Readiness

Кратко сообщи:

- какие документы изучены;
- готов ли Pilot‑003 к запуску;
- есть ли блокирующие противоречия;
- какие данные о материале отсутствуют.

### B. Каркас Pilot-003

Подготовь полный документ:

```text
Editors/Coach/Pilots/Pilot-003.md
```

Статус первоначальной версии:

```text
Planned
```

Документ должен быть заметно компактнее Pilot‑002 и включать только:

- паспорт;
- назначение;
- предмет проверки;
- границы;
- проверяемую модель;
- связь с `VIA-2026-014`;
- роли;
- критерии успешности;
- порядок Observation;
- условия запуска;
- условия завершения;
- место для итогового решения Owner.

Не включай заранее результаты, которых ещё нет.

Верни документ одним цельным Markdown-блоком.

### C. Начальный каркас VIA

На основании актуального Template подготовь начальную версию:

```text
VIA/2026/VIA-2026-014.md
```

На первом шаге заполни только:

- название документа с временным обозначением материала, если название ещё неизвестно;
- компактный паспорт;
- раздел `# 1. Formation`;
- поля для исходной идеи Owner;
- места для ранних редакторских входов;
- место для `Coach — Editorial Brief`.

Остальные разделы Template сохрани как пустую структуру, не заполняя будущие результаты.

Верни VIA одним цельным Markdown-блоком.

### D. Один запрос Owner

Если конкретный материал ещё не определён, задай Owner один собранный запрос, необходимый для начала Formation.

Запрос должен попросить передать:

- рабочее название или тему;
- исходную идею;
- существующий черновик, заметки или ссылки, если они есть;
- предполагаемую связь с серией;
- желаемый практический результат материала;
- существенные ограничения.

Не дроби этот запрос на последовательность мелких вопросов.

## 11. Условие фактического запуска

После получения данных о материале:

1. внеси их в `VIA-2026-014`;
2. определи достаточный объём Formation;
3. подготовь первые короткие задания для ранних редакторских входов;
4. представь Owner цельный стартовый пакет;
5. запроси одно решение:

```text
Запустить Pilot-003 и перевести его из Planned в Active?
```

До подтверждения Owner сохраняй статус Pilot‑003:

```text
Planned
```

После подтверждения:

```text
Active
```

Не переходи к блоку `Draft`, пока:

- не завершены необходимые входы Formation;
- Coach не подготовил Compact Editorial Brief;
- Owner не подтвердил направление материала.
