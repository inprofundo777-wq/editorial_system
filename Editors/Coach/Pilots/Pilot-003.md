# Pilot-003 — Master Editorial Assignment to Coach

## Pilot of Simplified Editorial Production Model

### Статус документа

**Master Editorial Assignment**

Этот документ является исходным редакционным заданием **Master Editor → Editorial Coach** для подготовки и проведения `Pilot-003`.

Он определяет:

* зачем проводится Pilot-003;
* какую модель он проверяет;
* стратегические границы пилота;
* обязательные элементы маршрута;
* роли и зоны ответственности;
* критерии успешности;
* границы полномочий Coach;
* ожидаемый результат пилота.

Coach принимает эту рамку как исходную.

Настоящий документ является единственным документом рамки `Pilot-003`.

Отдельный операционный документ Pilot не создаётся.

На основании настоящего задания Editorial Coach должен:

1. подготовить `VIA/2026/VIA-2026-014.md`;
2. получить от Owner исходный материал или идею;
3. провести материал через утверждённую производственную модель;
4. вести состояние и результаты работы непосредственно в VIA;
5. провести итоговый `Observation`;
6. представить Owner результат материала и результат Pilot.

Рабочая конструкция Pilot:

```text
Pilot-003.md
Master Assignment и рамка Pilot
        ↓
VIA/2026/VIA-2026-014.md
единый рабочий документ материала
        ↓
реальный редакционный цикл
        ↓
Observation
        ↓
Owner Decision
```

`Pilot-003.md` не дублирует работу над материалом.

`VIA-2026-014.md` не создаёт новую архитектуру Pilot, а реализует заданную здесь рамку на одном реальном материале.

# 1. Назначение Pilot-003

Pilot-003 является следующим эксплуатационным экспериментом Editorial System In Profundo после Pilot-001 и Pilot-002.

Его задача — проверить в работе не отдельную роль Coach, а **обновлённую производственную модель Editorial System** на одном реальном longform-материале.

Pilot-003 должен проверить:

* новую упрощённую структуру VIA;
* семиблочную производственную модель;
* отдельный блок Observation;
* расширенный состав редакторов;
* короткие задания с заранее обозначенным ожидаемым результатом;
* Independent Reviews;
* Coach Integrated Review;
* цельную Revision;
* локальный Final Check;
* более ясные передачи работы между редакторами;
* снижение ручной и административной нагрузки Owner.

Дополнительной задачей Pilot-003 становится наблюдение за **контрактами передачи между ролями**, прежде всего:

```text
Master Editor
→ Editorial Coach
→ специализированные редакторы
→ Coach Integration
→ Revision
→ Master / Owner
```

Pilot-003 не является автоматическим утверждением новой архитектуры.

Полученные результаты должны использоваться как практические данные для последующей ревизии Editorial System и Editor Renewal.

# 4. Проверяемая производственная модель

Pilot-003 использует семь последовательных производственных блоков:

```text
1. Formation
2. Draft
3. Review
4. Revision
5. Final Check
6. Publication
7. Distribution
```

После основного производственного цикла проводится:

```text
8. Observation
```

`Observation` не является восьмым производственным этапом материала.

Его задача — отделить:

```text
результат материала
```

от

```text
наблюдений о работе Editorial System
```

---

## Review

Внутри блока `Review` обязательно различаются:

```text
Independent Reviews
→ Coach Integrated Review
```

Independent Reviews сохраняют независимость редакторских компетенций.

Coach не должен заранее сводить редакторов к общему мнению.

После получения независимых Reviews Coach:

* выявляет повторяющиеся замечания;
* устраняет дублирование;
* различает обязательные исправления и рекомендации;
* отмечает реальные конфликты между Reviews;
* формирует одно ясное направление Revision.

---

## Publication

Внутри `Publication` могут находиться:

* Final Text;
* SEO Package;
* Visual;
* Publication Data;
* Published Page Check;
* Article Cycle Close.

Эти элементы не становятся автоматически отдельными производственными блоками.

# 5. Связанный VIA

Pilot-003 использует:

```text
VIA/2026/VIA-2026-014.md
```

Единственным действующим основанием структуры VIA является:

```text
Templates/VIA-YYYY-NNN.md
```

VIA должен оставаться **единым читаемым рабочим документом развития материала**.

Главный принцип:

> один материал — один рабочий VIA.

Не создавать параллельные документы для отдельных этапов, если этого не требует реальная работа.

Не возвращать в VIA административные конструкции старых версий только потому, что они использовались ранее.

Без практической необходимости не добавлять:

* подробную таблицу всех переходов;
* повторяющиеся статусы;
* отдельный статус каждой роли;
* обязательные записи `Not Required`;
* длинную историю изменений;
* реестр нормативных документов;
* повторяющиеся Owner Decisions;
* отдельный документ на каждый производственный этап;
* формальную систему A / B / C;
* новые постоянные чек-листы;
* новую нормативную архитектуру.

# 6. Контракт Master Editor → Coach

Это ключевая граница Pilot-003.

## Master Editor определяет

Master Editor задаёт стратегическую рамку Pilot-003:

* назначение пилота;
* предмет проверки;
* производственную модель;
* ключевые ограничения;
* состав рассматриваемых редакционных компетенций;
* критерии успешности;
* место пилота в развитии Editorial System;
* редакционную задачу материала после её утверждения Owner;
* существенные условия, которые Coach не должен изменять самостоятельно.

Master Editor не обязан проектировать каждую рабочую передачу внутри Pilot.

---

## Editorial Coach определяет

Получив Master Editorial Assignment, Coach отвечает за операционную реализацию.

Coach вправе:

* определить практическую последовательность работы внутри утверждённых блоков;
* определить достаточный объём Formation;
* подготовить короткие задания редакторам;
* определить, когда конкретная компетенция действительно необходима;
* организовать Independent Reviews;
* интегрировать Reviews;
* направить Revision;
* назначить необходимые локальные re-check;
* вести VIA;
* фиксировать Pilot Observations;
* предлагать улучшения системы как Observation.

---

## Coach не должен самостоятельно

* менять стратегическую цель Pilot-003;
* менять предмет проверки;
* заменять утверждённую производственную модель другой;
* создавать новую нормативную архитектуру;
* переопределять роль Pilot-003;
* менять редакционную цель материала;
* выбирать материал вместо Owner;
* превращать временную пилотную практику в постоянное правило;
* изменять документы Editorial System;
* создавать Accepted Decision;
* переписывать роли редакторов;
* подменять Master Editor;
* принимать фундаментальные содержательные решения вместо Owner.

Если Coach считает изменение стратегической рамки необходимым, он должен оформить:

```text
Coach Observation / Recommendation
```

и вернуть вопрос Master Editor / Owner.

## Точки решения Owner

Owner сохраняет исключительное право:

- выбрать материал для Pilot-003;
- передать исходную идею, текст или редакционную задачу;
- утвердить или изменить редакционную цель материала;
- принять существенные содержательные решения;
- выбрать направление при реальном конфликте редакторских рекомендаций;
- утвердить Final Text;
- разрешить публикацию;
- принять итог материала;
- принять итог Pilot;
- определить дальнейшую судьбу системных наблюдений.

Coach не должен запрашивать решение Owner после каждого производственного действия.

Owner подключается только тогда, когда:

- требуется выбрать направление материала;
- редакторы выявили существенную содержательную проблему;
- изменение затрагивает утверждённую цель;
- существует реальный конфликт рекомендаций;
- необходимо утвердить Final Text;
- требуется разрешение на публикацию;
- принимается итог Pilot.

Если решение Owner не требуется, Coach самостоятельно организует следующий рабочий шаг в пределах настоящего задания.

## Ответственность Coach за проведение материала

После создания VIA и получения материала Coach отвечает за непрерывность процесса.

Coach должен:

- определить достаточный маршрут каждого производственного блока;
- выдавать редакторам короткие задания;
- получать цельные Markdown-результаты;
- обеспечивать их перенос в VIA;
- определять следующий редакционный шаг;
- возвращать Owner только реальные точки решения;
- не оставлять Owner ответственным за техническую координацию редакторов;
- довести материал до завершения основного редакционного цикла;
- провести Observation после завершения работы над материалом.

Coach не ограничивается подготовкой VIA или рекомендацией маршрута.

Ожидаемый результат задания — практически проведённый материал, а не проект будущего процесса.

# 7. Состав Pilot-003

Pilot-003 намеренно использует расширенный набор компетенций.

Цель — не доказать необходимость всех ролей, а получить данные о том:

* какие входы реально полезны;
* где возникает дублирование;
* какие роли нужны постоянно;
* какие должны подключаться селективно.

## Formation

Предварительно рассматриваются:

* Owner;
* Strategy Editor;
* SEO Editor;
* Reader Board;
* Editorial Coach.

## Draft

* Longform Editor.

## Review

Independent Reviews:

* Literary Editor;
* Theology Editor;
* Reader Board;
* Strategy Editor;
* SEO Editor.

Integration:

* Editorial Coach.

## Revision

* Longform Editor.

## Final Check

Только редакторы, чьи существенные замечания требуют проверки:

* необходимые специализированные редакторы;
* Editorial Coach;
* Owner — при наличии реальной точки решения.

## Publication

По необходимости:

* Longform Editor;
* SEO Editor;
* Visual Editor;
* Editorial Coach;
* Owner.

## Distribution

Подключаются только компетенции, необходимые для конкретных платформенных материалов.

Расширенный состав не означает обязательного повторного подключения каждой роли на каждом блоке.

# 8. Принцип работы редакторов

Каждая редакторская передача должна быть короткой и предметной.

Coach передаёт редактору:

1. текущий блок;
2. ссылку на актуальный VIA;
3. конкретную задачу;
4. ожидаемый результат;
5. ограничения;
6. точный раздел VIA, для которого готовится результат.

Редактор возвращает:

> цельный Markdown-результат, пригодный для непосредственного переноса в VIA.

Не запрашивать:

* пересказ всего материала;
* формальный отчёт ради отчёта;
* повтор работы другой роли;
* полный Review, если требуется локальный re-check;
* разработку Editorial System;
* создание параллельного VIA;
* административную информацию, которая не влияет на материал.

# 9. Особая задача Pilot-003 — наблюдение за ролями

Pilot-003 проходит одновременно с подготовкой будущего `Editor Renewal`.

Поэтому пилот должен дать реальные наблюдения о работе редакторов.

Для каждой подключённой компетенции желательно фиксировать только практически значимые наблюдения:

* какую ценность роль внесла;
* на каком этапе она была наиболее полезна;
* что дублировала;
* чего ей не хватало;
* какие границы роли оказались неясными;
* что произошло при передаче работы следующему редактору.

Pilot-003 не переписывает документацию редакторов.

Он поставляет **эмпирический материал для их будущего Review**.

# 10. Ключевые вопросы Pilot-003

Pilot должен собрать практические данные по следующим вопросам.

### Производственная модель

1. Достаточны ли семь производственных блоков?
2. Помогает ли отдельный `Observation`, не усложняя цикл?
3. Достаточен ли новый VIA для восстановления состояния материала?
4. Можно ли закрывать основной цикл статьи независимо от полного завершения Distribution?

### Owner workload

5. Снизилось ли количество ручных передач?
6. Приходится ли Owner вручную собирать и форматировать ответы редакторов?
7. Где Owner всё ещё становится обязательным техническим посредником?

### Минимальные показатели Owner workload

В ходе Pilot Coach фиксирует, возникали ли следующие события:

- Owner вручную собирал единый результат из нескольких сообщений;
- Owner повторно запрашивал цельный Markdown-блок;
- Owner исправлял формат редакторской передачи;
- Owner вручную переносил сведения между документами или редакторами;
- Owner определял следующий технический шаг вместо Coach;
- процесс останавливался из-за неясности ответственности;
- одно решение Owner требовалось повторно фиксировать в нескольких местах.

Для каждого события достаточно результата:

```text
возникло / не возникло
```

Если событие возникло, Coach кратко указывает:

- производственный блок;
- причину;
- влияние на процесс.

Отдельный административный журнал не создаётся.

Итоговая оценка Owner workload включается одним блоком в `Observation`.

### Редакторские передачи

8. Работают ли короткие задания с заранее обозначенным результатом?
9. Понимает ли следующий редактор, что именно получает от предыдущего этапа?
10. Какие контракты передачи необходимо будет сформализовать позже?

### Formation

11. Какие ранние редакторские входы действительно влияют на Draft?
12. Какие Formation-входы оказываются избыточными?

### Review

13. Где возникает дублирование Independent Reviews?
14. Возникают ли реальные содержательные противоречия?
15. Способен ли Coach превратить независимые Reviews в одно ясное направление Revision?

### Revision / Final Check

16. Получается ли Revision цельной, а не механической?
17. Достаточен ли локальный Final Check?

### Роли

18. Какие роли выглядят постоянными?
19. Какие роли должны подключаться селективно?
20. Какие редакционные функции отсутствуют в текущей системе?
21. Какие границы между ролями требуют пересмотра?

### Система

22. Какие элементы нового VIA требуют уточнения?
23. Какие наблюдения должны перейти в Editor Renewal?
24. Какие изменения следует проверить ещё на Pilot-004 / Pilot-005 прежде, чем документировать постоянно?

# 11. Ограничения Pilot-003

Во время пилота:

* не изменять Editorial System;
* не создавать Accepted Decision;
* не переписывать документы редакторов;
* не создавать новые постоянные роли только на основании одного случая;
* не создавать новую документацию производственных блоков;
* не вводить формальную систему A / B / C;
* не создавать автоматизацию;
* не расширять Pilot за пределы одного реального longform-материала;
* не исправлять автоматически противоречия между фундаментальными документами;
* не заполнять VIA вымышленными данными;
* не превращать Observation в параллельный процесс;
* не увеличивать административную нагрузку Owner ради полноты документации.

Главный принцип:

> Pilot-003 существует для проверки работы системы, а не для строительства новой системы внутри самого Pilot.

# 13. Подготовка VIA-2026-014

Coach должен подготовить:

```text
VIA/2026/VIA-2026-014.md
```

на основании действующего:

```text
Templates/VIA-YYYY-NNN.md
```

VIA должен быть адаптирован к проверяемой производственной модели:

```text
Formation
→ Draft
→ Review
→ Revision
→ Final Check
→ Publication
→ Distribution
```

После производственного цикла:

```text
Observation
```

VIA должен оставаться единым читаемым документом.

Не создавать отдельные рабочие документы для:

- Formation;
- Draft;
- отдельных Reviews;
- Coach Integration;
- Revision;
- Final Check;
- Publication;
- Distribution;
- Observation.

Результаты редакторов должны возвращаться цельными Markdown-блоками, пригодными для непосредственного внесения в соответствующий раздел VIA.

## Минимальная начальная структура VIA

Первичная версия `VIA-2026-014.md` должна содержать:

1. компактный паспорт материала;
2. исходное состояние;
3. Formation;
4. Draft;
5. Review;
6. Revision;
7. Final Check;
8. Publication;
9. Distribution;
10. Observation;
11. Owner Decisions;
12. итоговое закрытие материала и Pilot.

Будущие результаты не заполняются заранее.

Допускается обозначить будущие разделы заголовками, но нельзя:

- придумывать отсутствующие решения;
- заполнять разделы формальным `Not Required`;
- создавать фиктивные результаты редакторов;
- дублировать один статус в нескольких местах;
- вести подробную административную историю без практической необходимости.

## Начальное состояние VIA

До выбора материала Owner в VIA фиксируются только:

- идентификатор;
- связь с `Pilot-003.md`;
- назначение документа;
- проверяемая производственная модель;
- статус ожидания материала;
- место для исходного материала Owner.

После получения материала Coach вносит:

- рабочее название;
- формат;
- исходную идею или текст;
- контекст;
- редакционную задачу;
- известные ограничения;
- первое решение о маршруте Formation.

- Coach определил достаточный маршрут Formation;

Дата фактического запуска фиксируется в VIA.

Отдельного решения о создании нового Pilot-документа не требуется.

# 15. Первое действие Coach после принятия задания

После получения настоящего Master Editorial Assignment Coach должен выполнить следующую последовательность.

## Шаг 1. Подтвердить контракт

Coach кратко подтверждает, что:

- принимает стратегическую рамку;
- не создаёт отдельный операционный Pilot;
- подготовит `VIA-2026-014.md`;
- будет вести материал непосредственно в VIA;
- принимает ответственность за координацию полного цикла;
- будет возвращать Owner только реальные точки решения.

## Шаг 2. Подготовить VIA

Coach создаёт полный начальный Markdown-документ:

```text
VIA/2026/VIA-2026-014.md
```

Начальная версия должна быть готова к внесению реального материала без дополнительного архитектурного проектирования.

## Шаг 3. Вернуть Owner один стартовый пакет

Coach возвращает одним сообщением:

1. краткое подтверждение принятия задания;
2. полный `VIA-2026-014.md` в Markdown;
3. краткое объяснение начальной структуры;
4. один запрос к Owner — передать или утвердить материал для Pilot-003.

Не разбивать стартовый пакет на серию мелких сообщений.

## Шаг 4. Начать Formation

После получения материала Coach:

1. вносит исходные данные в VIA;
2. определяет, какие ранние компетенции действительно нужны;
3. подготавливает первое редакторское задание;
4. запускает Formation;
5. продолжает процесс без нового общего проектирования Pilot.

# 16. Проведение Formation

В `Formation` должны последовательно появиться:

- исходная идея, текст или материал Owner;
- редакционная цель;
- предполагаемый читатель;
- место материала в проекте;
- существенные ограничения;
- только необходимые ранние редакторские входы;
- Coach Integrated Formation;
- цельный Editorial Brief для Longform Editor.

Coach не обязан подключать все потенциальные Formation-компетенции.

Каждое подключение должно отвечать на вопрос:

> Повлияет ли этот вход на направление и качество Draft?

Если влияние отсутствует, компетенция не подключается только ради полноты Pilot.

## Условие завершения Formation

Formation считается завершённым, когда:

- исходный материал достаточно понятен;
- редакционная цель сформулирована;
- читатель и контекст определены;
- существенные ограничения выявлены;
- необходимые ранние входы получены;
- Coach интегрировал результаты;
- подготовлен цельный Editorial Brief;
- Longform Editor может начать Draft без восстановления скрытого контекста.

Coach подтверждает операционную готовность Brief.

Если Formation выявил существенный выбор направления, который Owner ещё не утверждал, Coach возвращает Owner одну ясную точку решения.

После решения Owner Coach обновляет Brief и передаёт материал в Draft.

# 17. Проведение производственного цикла

После завершения Formation Coach проводит материал по следующему маршруту:

```text
Formation
→ Draft
→ Independent Reviews
→ Coach Integrated Review
→ Revision
→ Final Check
→ Publication
→ Article Cycle Close
```

Параллельно или после публикации:

```text
Distribution
```

После завершения производственной работы:

```text
Observation
→ Owner Decision
→ Pilot Close
```

## Draft

Coach передаёт Longform Editor:

- ссылку на VIA;
- цельный Editorial Brief;
- конкретную задачу;
- ожидаемый формат Draft;
- ограничения;
- точный раздел VIA для результата.

Результатом должен стать цельный Draft, пригодный для следующего блока.

## Review

Coach организует Independent Reviews, сохраняя независимость редакторов.

Каждый редактор получает:

- актуальную версию Draft;
- задачу своей компетенции;
- границы Review;
- ожидаемый цельный Markdown-результат.

После получения Reviews Coach формирует `Coach Integrated Review`, в котором:

- объединяет повторяющиеся замечания;
- различает обязательные исправления и рекомендации;
- обозначает конфликты;
- не стирает важные различия между компетенциями;
- формирует одно ясное задание на Revision;
- выделяет реальные точки решения Owner.

## Revision

Longform Editor получает:

- актуальный Draft;
- Coach Integrated Review;
- решения Owner, если они потребовались;
- одно цельное задание на Revision.

Результатом должна стать цельная новая версия текста, а не набор локальных исправлений.

## Final Check

Coach назначает только необходимые локальные проверки.

Полный повтор всех Reviews не проводится без содержательной причины.

Final Check должен установить:

- устранены ли обязательные проблемы;
- не возникли ли новые существенные нарушения;
- готов ли текст к решению Owner;
- какие вопросы, если они остались, действительно требуют решения.

## Publication

После утверждения Final Text Owner Coach координирует подготовку:

- SEO Package;
- Visual;
- Publication Data;
- итогового текста для публикации;
- проверки опубликованной страницы.

Основной цикл статьи может быть закрыт после того, как:

- Final Text утверждён;
- обязательный публикационный пакет подготовлен;
- Owner разрешил публикацию;
- материал опубликован;
- опубликованная страница проверена;
- существенные ошибки отсутствуют или исправлены.

## Distribution

Для практической проверки Distribution должен быть подготовлен и опубликован хотя бы один реальный платформенный материал, связанный со статьёй.

Полное завершение всех возможных платформенных публикаций не является условием закрытия основного цикла статьи.

Если дополнительные материалы продолжаются после `Article Cycle Close`, в VIA фиксируются:

- что уже подготовлено;
- что опубликовано;
- что осталось;
- кто отвечает за следующий шаг.

# 18. Непрерывность процесса

После запуска Pilot Coach отвечает за определение следующего конкретного шага.

После каждого завершённого блока Coach должен:

1. внести или подготовить для внесения результат в VIA;
2. кратко определить состояние материала;
3. назвать следующий производственный блок;
4. подготовить следующее задание;
5. вернуть Owner точку решения только при реальной необходимости.

Coach не должен завершать сообщение неопределёнными формулами:

```text
можно продолжить
```

```text
следует решить, что делать дальше
```

если следующий шаг уже определяется настоящей производственной моделью.

Предпочтительный формат перехода:

```text
Блок завершён: Formation
Результат: Editorial Brief
Следующий блок: Draft
Следующее действие: передача Longform Editor
Решение Owner: не требуется
```

# 19. Observation

После завершения производственной работы Coach проводит отдельный `Observation`.

Observation не изменяет уже завершённый материал и не становится новой редакционной стадией.

В нём должны быть отдельно рассмотрены:

## Результат материала

- прошёл ли материал предусмотренный маршрут;
- был ли опубликован;
- был ли запущен Distribution;
- какие существенные проблемы остались.

## Производственная модель

- были ли достаточны семь блоков;
- какие границы между блоками работали неясно;
- можно ли было восстановить состояние материала по VIA;
- не возникли ли параллельные процессы.

## Owner workload

- какие события из минимальных показателей возникли;
- где Owner оставался содержательной точкой решения;
- где Owner становился техническим посредником;
- снизилась ли нагрузка по сравнению с Pilot-002.

## Контракты передачи

- какие передачи работали;
- где требовалось повторное объяснение;
- какие результаты приходилось пересобирать;
- какие контракты следует проверить ещё раз.

## Роли

Для каждой реально подключённой компетенции:

- внесённая ценность;
- наиболее полезный блок;
- дублирование;
- неясные границы;
- необходимость постоянного или селективного подключения.

## Рекомендации

Наблюдения распределяются на:

```text
подтверждено практикой
```

```text
требует повторной проверки
```

```text
кандидат для Pilot-004 / Pilot-005
```

```text
вопрос для будущего Editor Renewal
```

Observation не создаёт автоматически:

- новое правило;
- Accepted Decision;
- Backlog-запись;
- Development Proposal;
- изменение документации редакторов.

# 20. Критерии успешности Pilot-003

Pilot-003 считается успешно проведённым, если:

- создан и использован `VIA-2026-014.md`;
- VIA оставался единым рабочим документом;
- один реальный longform-материал прошёл основной цикл;
- Formation завершился цельным Editorial Brief;
- Draft был подготовлен;
- Independent Reviews сохранили самостоятельность;
- Coach подготовил Integrated Review;
- Revision была цельной;
- Final Check был локальным и достаточным;
- Owner утвердил Final Text;
- материал был опубликован;
- опубликованная страница была проверена;
- был выпущен хотя бы один Distribution-материал;
- Observation был проведён отдельно от работы над материалом;
- Owner получил итоговый результат одним цельным пакетом;
- Pilot дал практические данные для последующих пилотов.

Успешность Pilot не требует отсутствия всех проблем.

Pilot может получить итог:

```text
Successful
```

```text
Successful with Required Revisions
```

```text
Inconclusive
```

```text
Unsuccessful
```

Итог определяет Owner после рассмотрения Pilot Report.

# 21. Условия завершения

Материальная часть Pilot считается завершённой, когда:

- Final Text утверждён;
- статья опубликована;
- Published Page Check выполнен;
- основной Article Cycle закрыт;
- хотя бы один Distribution-материал опубликован либо Owner отдельно разрешил закрытие без него.

Системная часть Pilot считается завершённой, когда:

- Observation подготовлен;
- результат Master → Coach handoff оценён;
- Owner workload оценён;
- работа ролей рассмотрена;
- рекомендации для последующих пилотов сформулированы;
- Pilot Report представлен Owner.

Pilot-003 закрывается только после решения Owner.
