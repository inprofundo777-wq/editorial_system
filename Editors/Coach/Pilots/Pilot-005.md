# Pilot-005 — Review Task Compression / Minimal Review Mode

## Статус

**Planned / Ready to Launch**

## Материал

```text
Portfolio item:
Покой среди будней

Source:
Development/Experiments/EXP-001-Content-Portfolio.md

Production VIA:
VIA/2026/VIA-2026-016.md
```

Pilot-005 является следующим ограниченным производственным экспериментом после Pilot-004.

Он проверяет не сокращение компетенций Editors, а возможность использовать их полную компетентность через более лёгкий базовый режим Review.

Pilot-005 не утверждает постоянные Roles, Modes, Levels или Stage Colleges.

---

# 1. Что сохраняется из предыдущего опыта

Предыдущие Pilot, VIA Role/Task Retrospective и Role Reviews показали, что специализированные Editors накопили существенно более широкий набор подтверждённых функций, чем требуется вызывать в каждом стандартном Review.

Полный объём компетенций сохраняется.

Pilot-005 не означает:

```text
Literary умеет только композицию

Theology умеет только искать overclaim

Reader умеет смотреть только одну аудиторию
```

Рабочая гипотеза другая:

```text
FULL ROLE CAPABILITY
        ↓
режим применения
        ↓
MINIMAL / STANDARD / DEEP ?
```

В Pilot-005 проверяется только минимальный режим.

Если Editor обнаруживает серьёзный риск вне базового чек-листа, его полная компетенция остаётся доступной и может быть развёрнута в более глубокий Review.

Role Reviews остаются аналитическим источником полного диапазона функций и в дальнейшем могут использоваться при оформлении:

- Role Core;
- Checklists;
- Modes;
- Levels;
- Stage compositions.

---

# 2. Главная гипотеза Pilot

Можно ли сохранить качество Review, если Editor:

1. использует короткий компетентностный checklist;
2. не выдаёт полный отчёт по каждому пункту;
3. возвращает только material risks;
4. расширяет Review только там, где риск действительно требует анализа.

Рабочая модель:

```text
Checklist
    ↓
silent scan
    ↓
risk detected?
   /        \
 NO         YES
 ↓           ↓
short       focused
verdict     risk review
```

Таким образом, checklist является инструментом внутренней проверки Editor, а не формой обязательного отчёта.

---

# 3. Основные гипотезы

## H1 — Upstream Sufficiency

Закрытая Portfolio Card позволяет Coach сформировать достаточный Editorial Brief без повторного Strategy / SEO / Reader Formation.

## H2 — Risk-based Review

Literary, Theology и Reader способны использовать короткий checklist и возвращать только material findings без потери существенной информации.

## H3 — Target Audience Review

Reader может провести полезную проверку прежде всего относительно основной аудитории материала и потенциально заинтересованной аудитории, не разворачивая полный Reader Board.

## H4 — Reduced Owner Load

Review становится короче и легче для Owner, сохраняя возможность в любой момент вызвать полный capability роли или более глубокий Mode.

---

# 4. Рабочая цепочка

```text
Closed Portfolio Card
        ↓
Coach Brief
+ Audience
        ↓
Longform Draft
        ↓
Literary Risk Check
Theology Risk Check
Reader Audience Risk Check
        ↓
Coach Integration
        ↓
Longform Revision
        ↓
External Literary Control
        ↓
Final Text
        ↓
Selective Final Check
        ↓
SEO Publication
        ↓
Publication
        ↓
Close / Observation
```

Strategy и SEO не входят в стандартный Draft Review.

Они сохраняются как доступные capabilities и могут быть подключены при material deviation.

# 5. Process Map

В VIA сохраняется принцип единого рабочего интерфейса:

| Блок | Шаг | Статус |
|---|---|:---:|
| **Formation** | Portfolio → Coach Brief | 0 |
| **Draft** | Longform Draft | - |
| **Review** | Literary Risk Check | - |
| | Theology Risk Check | - |
| | Reader Audience Risk Check | - |
| | Coach Integrated Review | - |
| **Revision** | Longform Revision | - |
| **Finalization** | External Literary Control | - |
| | Final Text | - |
| **Final Check** | Required Re-checks | - |
| **Publication** | SEO Publication Package | - |
| | Visual / Technical Preparation | - |
| | Publication | - |
| **Close** | Publication Close | - |
| **Observation** | Pilot Observation | - |

Статусы:

```text
-  не активирован
0  активен
+  завершён
```

Принцип передачи не меняется:

```text
Owner получает результат
→ переносит Markdown в VIA
→ 0 меняет на +
→ следующий - меняет на 0
→ передаёт ту же ссылку
```

Редактор физически открывает актуальную версию VIA по ссылке.

Не создавать заранее пустые секции под Editors.

---

# 6. Coach Formation

Coach получает закрытую Portfolio Card и формирует минимальный Brief.

Не проводить повторный:

- Candidate Selection;
- Strategy Review;
- SEO Review;
- Reader Board.

## Brief должен определить

- центральный жизненный вопрос;
- функцию материала;
- богословскую / смысловую ось;
- основные границы;
- связь с корпусом;
- Audience;
- конкретный Longform Assignment.

---

# 7. Audience

Не требуется чрезмерно узкая persona.

Coach определяет:

## Primary Audience

Для кого прежде всего существует этот материал.

## Relevant Audience

Кому ещё тема может быть естественно интересна или полезна.

Формат должен быть коротким.

Пример логики:

```text
Primary Audience:
человек, живущий в постоянной нагрузке
и откладывающий внутренний покой
до момента, когда жизнь станет легче.

Relevant Audience:
люди, переживающие усталость,
ответственность, рутину,
внутреннюю перегруженность
или трудность остановиться.
```

Audience не должна превращаться в полный Reader Board до Draft.

---

# 8. Review Principle — Checklist + Traffic Light

Review в Pilot-005 работает как внутренняя проверка риска.

Editor проходит свой компетентностный checklist.

Для каждого пункта мысленно используется логика:

```text
GREEN
существенной проблемы нет

YELLOW
есть локальный риск,
но он не требует большого Review

RED
material risk,
способный изменить Revision
```

Editor не обязан возвращать список всех GREEN/YELLOW пунктов.

Основной Output создаётся только по RED и действительно существенным YELLOW findings.

Если material risk отсутствует:

```text
No material risk detected.
```

Допускается одна короткая рекомендация, если она полезна, но не требует Revision.

---

# 9. Literary Risk Check

Полная компетенция Literary сохраняется.

Источником полного диапазона навыков являются Role Review и действующая документация роли.

В минимальном Pilot Mode Editor прежде всего проверяет:

### Structure
- одно ли главное движение;
- нет ли конкурирующих смысловых центров;
- не повторяется ли уже доказанная мысль;
- работает ли порядок блоков;
- не распадается ли финал.

### Language
- естественно ли звучит текст;
- не стал ли он чрезмерно объясняющим;
- нет ли заметной искусственности;
- не теряется ли авторский голос.

### Rhythm
- не перегружен ли материал;
- нет ли провалов движения;
- не слишком ли много однотипных примеров или конструкций.

### Additional capability
Любой другой литературный риск из полного диапазона компетенции роли может быть поднят, если он material.

## Output

Если существенного риска нет:

```markdown
## Literary Review

No material risk detected.
```

Если есть:

```markdown
## Literary Review

**Risk:** RED / YELLOW

**Material finding:**  
...

**Why it matters:**  
...

**Required correction:**  
...

**Preserve:**  
...
```

Не требуется полный обзор текста.

---

# 10. Theology Risk Check

Полная компетенция Theology сохраняется.

В минимальном Pilot Mode прежде всего проверить:

### Scripture
- корректность контекста;
- допустимость применения;
- не говорит ли текст больше, чем основание Писания.

### Claim
- нет ли theological overclaim;
- не смешиваются ли описание и норма;
- корректно ли распределён субъект действия:
  Бог / Христос / человек.

### Christological center
- не превращается ли материал в психологическую или нравственную технику;
- остаётся ли центр во Христе.

### Pastoral risk
- не создаёт ли формулировка ложного обещания;
- духовного давления;
- оправдания вреда;
- опасного применения.

### Additional capability
Любой другой material theology risk из полного диапазона компетенции роли может быть поднят.

## Output

```markdown
## Theology Review

No material risk detected.
```

или:

```markdown
## Theology Review

**Risk:** RED / YELLOW

**Material finding:**  
...

**Scripture / theological basis:**  
...

**Required correction:**  
...

**Preserve:**  
...
```

---

# 11. Reader Audience Risk Check

В Pilot-005 Reader работает прежде всего относительно Audience, определённой Coach.

Он не моделирует полный набор возможных читателей.

Проверить:

### Recognition
- узнаёт ли Primary Audience своё состояние и вопрос.

### Pressure
- не превращается ли текст для неё в дополнительное требование или обвинение.

### Misreading
- какое существенное неверное прочтение наиболее вероятно.

### Takeaway
- что читатель, вероятнее всего, унесёт после текста.

### Relevant Audience
Если материал создаёт очевидный серьёзный риск для другой естественно связанной аудитории, Reader может поднять его как deviation.

Но не проводить широкий Reader Board по умолчанию.

## Output

```markdown
## Reader Review

No material audience risk detected.
```

или:

```markdown
## Reader Review

**Risk:** RED / YELLOW

**Audience:**  
Primary / Relevant

**Material finding:**  
...

**Likely reading:**  
...

**Required correction:**  
...
```

---

# 12. Strategy и SEO

## Strategy

Не вызывается в стандартном Review.

Подключается только если Draft:

- фактически стал другой статьёй;
- изменил функцию Portfolio Card;
- существенно расширил scope;
- создал новую смысловую линию уровня корпуса;
- требует пересмотра upstream-решения.

Полный диапазон Strategy capability сохраняется.

## SEO

Не вызывается для полного Draft Review по умолчанию.

Основной рабочий вызов:

```text
Final Text
→ SEO Publication
```

Draft-level SEO может быть вызван при material search deviation.

Это не означает сокращение компетенции SEO.

---

# 13. Coach Integration

Coach получает три независимых Risk Reviews.

Его задача:

- выделить material findings;
- убрать дубли;
- сохранить разные основания риска;
- определить Required Changes;
- определить, что сохранить;
- не добавлять рекомендации, не влияющие на Revision;
- сформировать одно цельное Revision Assignment.

## Output

```markdown
## Coach — Integrated Review

**Stage verdict:**  

### Material findings
1.
2.
3.

### Required changes
1.
2.
3.

### Preserve
-

### Do not add
-

### Revision assignment
...

### Required re-checks
...
```

Longform не получает три несведённых Review как задания.

---

# 14. Longform Revision

Longform получает:

- актуальный Draft;
- Coach Integrated Review.

Он возвращает один новый цельный Revised Draft.

Не требуется change log.

Не требуется комментарий к каждому Editor.

---

# 15. External Literary Control

После основной Revision проводится отдельный финальный прогон через внешний Literary Editor, исторически использовавшийся для мелкой литературной шлифовки.

Его функция отличается от основного Literary Review.

Основной Literary Review:

```text
Draft
→ диагностирует material literary risks
→ влияет на Revision
```

External Literary Control:

```text
Revised Draft
→ финальная литературная свежесть
→ небольшие рекомендации
→ polish
```

## Задача

Проверить:

- шероховатости языка;
- локальные повторы;
- неестественные фразы;
- ритмические мелочи;
- чрезмерно гладкие / искусственные конструкции;
- возможные AI-patterns;
- небольшие места, где текст можно сделать естественнее или точнее.

Внешний Editor не должен заново открывать:

- структуру статьи;
- богословскую концепцию;
- стратегию;
- основную Revision.

## Expected result

Обычно:

```text
READY
+ несколько рекомендаций
```

или:

```text
LOCAL POLISH REQUIRED
```

Если внешний Editor обнаруживает material structural/theological issue, это считается deviation и возвращается Coach.

---

# 16. Final Text

После External Literary Control фиксируется единый Final Text.

Если рекомендации:

- необязательные — могут быть сохранены для будущей практики;
- локальные — выполняется лёгкая шлифовка;
- material — возвращаются Coach как deviation.

После этого Final Text считается входом в Selective Final Check / Publication.

---

# 17. Selective Final Check

Не проводить второй полный Review.

Coach определяет только те re-checks, которые действительно требуются по material findings.

Проверяется:

- выполнены ли Required Changes;
- не потеряно ли Preserve;
- не возник новый blocker;
- готов ли материал к Publication.

---

# 18. SEO Publication

SEO получает Final Text.

Основной Output:

- SEO title;
- meta description;
- slug;
- search intent;
- internal links;
- labels;
- alt при наличии Visual;
- необходимые Blogger fields;
- publication blockers.

Не повторять Portfolio analysis без material причины.

---

# 19. Observation

Pilot должен проверить не только качество статьи, но и режим использования компетенций.

Coach при закрытии фиксирует только существенное:

### Review compression
- был ли Review действительно короче;
- хватило ли Risk-based outputs для Revision.

### Capability preservation
- возникали ли findings вне минимального checklist;
- позволила ли модель Editor поднять их;
- понадобился ли Full / Deep Review.

### Audience
- была ли Audience достаточной;
- потребовался ли более широкий Reader analysis.

### Conditional calls
- понадобился ли Strategy;
- понадобился ли Draft-level SEO.

### External Literary Control
- дал ли он только polish;
- обнаружил ли material issue;
- был ли полезен как отдельный финальный слой.

### Owner load
- потребовалось ли дополнительное объяснение;
- пришлось ли Owner интегрировать результаты;
- работала ли передача через одну ссылку.

---

# 20. Критерий успеха

Pilot считается успешным, если:

- Portfolio Card достаточно для Formation;
- Audience помогает Longform и Reader;
- Editors сохраняют широкий профессиональный взгляд, но возвращают только material risks;
- отсутствие полного отчёта по checklist не приводит к потере существенного finding;
- Coach способен интегрировать короткие Reviews;
- Revision остаётся качественной;
- внешний Literary Control работает как лёгкий polish, а не второй полный Review;
- Strategy и SEO не нужны в стандартном Review без deviation;
- Owner работает преимущественно через ссылку, Markdown и статусы;
- итоговый VIA становится заметно компактнее.

---

# 21. Что Pilot сознательно не утверждает

Pilot-005 не утверждает:

- что роли сокращены до этого checklist;
- что минимальный Mode достаточен для любого материала;
- постоянные названия Modes;
- окончательную систему уровней;
- Review College;
- постоянное исключение Strategy или SEO;
- постоянный Audience contract;
- окончательную роль External Literary Editor;
- новый VIA template.

---

# 22. После Pilot

Результат должен использоваться в двух направлениях.

## A. Minimal Review Mode

Понять, достаточно ли минимального Risk-based режима для стандартной статьи.

## B. Role Capability Preservation

Сопоставить:

```text
Role Reviews
+
VIA Role/Task Retrospective
+
Pilot-005 evidence
```

и подготовить будущую модель:

```text
ROLE CORE
полный набор компетенций
        ↓
CHECKLIST
что роль способна проверять
        ↓
MODE / LEVEL
какой объём проверки вызывается сейчас
        ↓
OUTPUT CONTRACT
что нужно вернуть в конкретном процессе
```

Полный capability checklist не должен строиться только по Pilot-005.

Для него дополнительно использовать документы:

```text
Development/Proposals/Role-Reviews/
```

включая:

- Longform;
- Literary;
- Theology;
- Reader;
- Strategy;
- SEO.

# 23. Следующий возможный эксперимент

Если Minimal Review Mode подтверждается:

```text
Role Reviews
+ Retrospective
+ Pilot-005
        ↓
Stage × Capability Map
        ↓
Review Mode / Level model
        ↓
при достаточном evidence
        ↓
Review College experiment
```

College должен собираться не из урезанных ролей, а из необходимых Modes полной компетенции.
