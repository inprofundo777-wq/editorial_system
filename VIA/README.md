# VIA — Operational Protocol

# Паспорт документа

| Поле | Значение |
|---|---|
| **Документ** | VIA Operational Protocol |
| **Путь** | `VIA/README.md` |
| **Версия** | `1.0-working` |
| **Статус** | Working Protocol / Validation Required |
| **Тип** | Постоянный операционный документ |
| **Функция** | Canonical source of truth для общей логики VIA |
| **Координация** | Editorial Coach |
| **Владелец** | In Profundo Editorial System |
| **Validation** | `VIA-2026-018` и следующий новый VIA |

Этот документ определяет общие правила работы VIA.

Он подчинён Конституции и DNA In Profundo, согласуется с `Workflows/Article_Lifecycle.md` и не заменяет постоянную документацию редакционных ролей.

После утверждения настоящего документа общие правила VIA не должны полностью воспроизводиться:

- в VIA Template;
- в конкретных VIA;
- в локальных handoff;
- в документации отдельных Editors.

---

# 1. Назначение VIA

VIA — единый живой case file конкретного редакционного материала.

Каждый VIA:

- относится к одному материалу или одному редакционному циклу;
- имеет постоянный VIA ID;
- хранится в одном документе;
- сохраняет Source и закрытые upstream decisions;
- содержит Editorial Brief;
- показывает фактическое состояние работы;
- принимает результаты необходимых Editors;
- сохраняет Draft, Reviews, Revision и Final Text;
- фиксирует publication data;
- сохраняет material evidence;
- подготавливает необходимый Portfolio / Notion routing;
- после завершения остаётся частью истории материала.

VIA отвечает на вопросы:

- что происходит с этим материалом;
- какие решения уже закрыты;
- какие шаги доступны сейчас;
- какие результаты уже получены;
- что требуется следующему участнику;
- чем завершился редакционный цикл;
- какое material learning возникло.

VIA не является:

- полной копией Editorial System;
- документацией редакционных ролей;
- новым Content Portfolio;
- заменой Notion;
- отдельным системным Backlog;
- полным журналом всех технических действий;
- местом автоматического изменения архитектуры.

# 2. Границы документов

## 2.1. VIA Protocol

Настоящий документ отвечает:

> Как участники работают внутри VIA?

Здесь находятся:

- one-link protocol;
- статусная логика;
- Process Map authority;
- правила активации;
- handoff contract;
- общие границы стадий;
- progressive decision closure;
- правила Publication и Close;
- Observation;
- learning routing;
- manual transfer contract.

## 2.2. VIA Template

`Templates/VIA-YYYY-NNN.md` отвечает:

> Какой минимальный каркас нужен для создания нового VIA?

Template:

- реализует настоящий Protocol;
- не устанавливает самостоятельные нормы;
- не хранит историю экспериментов;
- не повторяет полную документацию ролей;
- не создаёт заранее пустые секции всех возможных Editors.

## 2.3. Конкретный VIA

Конкретный `VIA-YYYY-NNN.md` отвечает:

> Что происходит с этим материалом?

В нём остаются только:

- данные материала;
- фактическое состояние;
- article-specific handoff;
- закрытые решения;
- результаты работы;
- evidence;
- publication data;
- Close;
- material observations.

## 2.4. Role Documentation

Постоянная документация Editor отвечает:

> Как конкретная роль выполняет собственную capability?

В ней находятся:

- природа роли;
- authority;
- модель мышления;
- методы работы;
- профессиональные критерии;
- типичные риски;
- role-specific Output Contract;
- критерии PASS и material deviation;
- пределы вмешательства.

Общие правила VIA не создаются отдельно внутри каждой роли.

## 2.5. Development

`Development` используется для рассмотрения изменений Editorial System.

Observation внутри VIA:

- не является Proposal;
- не является принятым решением;
- не изменяет Protocol;
- не изменяет role documentation;
- не создаёт новую capability автоматически.

# 3. One-Link Protocol

Основной способ запуска Editor:

1. Owner передаёт одну актуальную ссылку на конкретный VIA.
2. Editor физически открывает документ по ссылке.
3. Память ветки или предыдущая версия VIA не заменяет актуальный GitHub-документ.
4. Editor читает Process Map.
5. Editor находит активный шаг, относящийся к его роли.
6. Editor читает соответствующий Active Handoff и необходимые article-specific inputs.
7. Editor выполняет только назначенную capability.
8. Editor возвращает результат по установленному Transfer Contract.
9. Owner физически переносит результат в GitHub и обновляет Process Map.
10. Следующий участник получает ту же актуальную ссылку.

Если по ссылке невозможно однозначно определить задачу, Editor не должен угадывать следующий шаг.

Он сообщает:

- какая информация отсутствует;
- какие строки Process Map противоречат друг другу;
- какой handoff не соответствует активному шагу;
- какое решение требуется до начала работы.

Такое затруднение может быть зафиксировано как Observation, если оно имеет значение для развития системы.

# 4. Состояние VIA

## 4.1. Два уровня состояния

В VIA различаются:

### Lifecycle Status

Состояние всего документа:

- `Active`;
- `Closed`;
- `Archived`.

Lifecycle Status хранится в паспорте VIA.

### Step Status

Состояние отдельных шагов:

- `-`;
- `0`;
- `+`.

Step Status хранится только в Process Map.

Эти два уровня не должны смешиваться.

Паспорт не используется для повторного указания текущего Stage.

---

# 5. Process Map — State Authority

Process Map является единственным canonical source of truth текущего рабочего состояния VIA.

Она размещается сразу после паспорта материала.

Process Map показывает:

- какие шаги завершены;
- какие шаги активны;
- какие шаги пока не активированы;
- какие capabilities могут работать параллельно;
- какие зависимые шаги ещё ожидают необходимых inputs.

Если паспорт, Active Handoff, локальный комментарий или память ветки расходятся с Process Map, действует Process Map.

Расхождение должно быть исправлено до продолжения зависимого шага.

---

# 6. Значения статусов

| Статус | Значение |
|:---:|---|
| `-` | Шаг не активирован, ещё не имеет необходимых inputs или не требуется в текущем состоянии |
| `0` | Шаг доступен для выполнения, находится в работе или ожидает установленного внешнего условия |
| `+` | Требуемый результат шага получен и зафиксирован |

Статус отражает рабочую доступность и завершённость шага.

Он не является:

- оценкой качества;
- приоритетом материала;
- глобальным статусом всей Editorial System;
- указанием, что во всём проекте может существовать только один активный процесс.

---

# 7. Несколько активных шагов

В одном VIA может существовать несколько шагов со статусом `0`.

Это допустимо, если:

- для каждого шага существуют необходимые inputs;
- задачи не требуют ещё не полученного результата друг друга;
- каждый шаг имеет отдельного исполнителя или capability;
- границы каждого задания понятны;
- завершение каждого шага можно определить независимо.

Несколько `0` могут находиться:

- внутри одного функционального блока;
- в разных функциональных блоках;
- в параллельных Reviews;
- в Observation;
- в Publication и предварительном Close.

Пример допустимой параллельной работы:

    | Блок | Шаг | Статус |
    |---|---|:---:|
    | Review | Theology Review | 0 |
    | Review | Reader Review | 0 |
    | Observation | Process Observation | 0 |

Пример допустимой работы перед публичной публикацией:

    | Блок | Шаг | Статус |
    |---|---|:---:|
    | Publication | Scheduled Publication | 0 |
    | Close | Preliminary Close | 0 |
    | Observation | Process Observation | 0 |

Количество `0` само по себе не является проблемой.

Главный критерий:

> Каждый активный шаг должен иметь необходимые inputs и не нарушать зависимость от ещё не завершённого обязательного шага.

---

# 8. Зависимости и активация

Шаг получает статус `0`, когда:

- существует необходимый Source;
- завершены обязательные upstream decisions;
- получены необходимые результаты предыдущих capabilities;
- назначен исполнитель;
- сформулирован article-specific handoff;
- понятен expected output;
- работа может начаться без угадывания отсутствующих решений.

Нельзя активировать зависимый шаг преждевременно.

Например:

- Coach Integrated Review не активируется до получения необходимых Independent Reviews;
- Longform Revision не активируется до готовности Integrated Review;
- обязательный Final Check не завершается до получения требуемого re-check;
- окончательный Close не завершается до выполнения установленных final conditions.

Функциональные блоки VIA не обязаны активироваться строго линейно.

Observation может идти параллельно с производством.

Предварительный Close может готовиться до фактической публичной публикации.

---

# 9. Изменение Process Map

При изменении состояния Owner физически обновляет Process Map на основании точной инструкции Coach или соответствующего Editor.

Обычный переход может выглядеть так:

    Theology Review: 0 → +
    Reader Review: оставить 0
    Coach Integrated Review: оставить -

После завершения второго обязательного Review:

    Reader Review: 0 → +
    Coach Integrated Review: - → 0

Editor не должен ограничиваться сообщением:

> Обновите статусы соответствующим образом.

Он должен указать точные строки и переходы.

После физического обновления Process Map отдельная инструкция `Process Map Update` не обязана сохраняться как постоянный раздел VIA.

Актуальная таблица уже является evidence текущего состояния.

История содержательной работы сохраняется в результатах Editors, а не в архиве технических команд изменения статуса.

---

# 10. Паспорт VIA

Паспорт конкретного VIA хранит устойчивые данные:

- VIA ID;
- рабочее или финальное название;
- Lifecycle Status;
- Source;
- Portfolio reference;
- Pilot, если применимо;
- Coordinator;
- дату открытия;
- дату закрытия после завершения.

Паспорт не должен содержать:

- текущий Stage;
- активного Editor;
- следующий шаг;
- подробное состояние Review;
- дублирование Process Map.

При обычном переходе между шагами паспорт не обновляется.

Lifecycle Status меняется только при изменении состояния всего VIA:

    Active → Closed → Archived

---

# 11. Active Handoff

Active Handoff содержит конкретное задание для шага, отмеченного `0`.

Если одновременно активны несколько независимых шагов, каждый получает отдельный handoff.

Пример структуры:

    ## Active Handoffs

    ### Theology Review — `0`

    Исполнитель: Theology Editor
    Inputs: ...
    Task: ...
    Required Boundaries: ...
    Expected Output: ...

    ### Reader Review — `0`

    Исполнитель: Reader Editor
    Inputs: ...
    Task: ...
    Required Boundaries: ...
    Expected Output: ...

Active Handoff содержит:

- исполнителя;
- точные inputs;
- article-specific задачу;
- material boundaries;
- закрытые decisions;
- expected output;
- место результата;
- необходимые Owner Actions.

Active Handoff не повторяет:

- всю Process Map;
- легенду статусов;
- общий VIA Protocol;
- полную документацию роли;
- историю предыдущих handoff;
- полное объяснение Editorial System.

Active Handoff не является самостоятельным источником состояния.

Если handoff не соответствует Process Map, работа не начинается до устранения расхождения.

# 12. Граница полномочий

## 12.1. Portfolio и Formation

Закрытый Content Portfolio определяет стратегический выбор материала.

VIA не повторяет Candidate Selection, если Portfolio decision уже закрыт.

Coach превращает Portfolio Handoff в достаточный Editorial Brief, но не проводит новый стратегический выбор без material deviation.

## 12.2. Independent Reviews

Review Editors:

- используют полный capability роли;
- ищут material risks;
- защищают необходимые boundaries;
- возвращают только downstream-useful findings;
- не проектируют новую статью;
- не создают конкурирующий Draft;
- не расширяют тему без material основания;
- не переоткрывают закрытые решения по умолчанию.

Конкретный Review scope определяется article-specific handoff.

Метод профессиональной проверки определяется permanent role documentation.

## 12.3. Coach Integration

Coach:

- сопоставляет material findings;
- устраняет overlap;
- различает required boundaries и optional suggestions;
- сохраняет protected ground;
- определяет необходимость re-check;
- формирует достаточный Revision Assignment;
- не создаёт ещё одну полную редактуру;
- не проектирует Revised Draft вместо Longform.

## 12.4. Longform Revision

Longform:

- соблюдает required boundaries;
- сохраняет protected ground;
- самостоятельно выбирает композиционное и языковое решение;
- не обязан механически выполнять optional suggestions;
- не переоткрывает закрытые upstream decisions без material deviation;
- возвращает один цельный Revised Draft.

## 12.5. Finalization

Finalization:

- работает с актуальным Final Candidate;
- устраняет только оставшиеся дефекты своей компетенции;
- не повторяет полный Review;
- не меняет тему, центральный конфликт или архитектуру без material deviation;
- возвращает PASS либо локально достаточные коррекции.

## 12.6. Final Check

Final Check проводится только для capabilities, которым действительно требуется повторная проверка.

Полный Review не повторяется по умолчанию.

## 12.7. Coach и архитектура

Coach:

- управляет конкретным VIA;
- классифицирует material learning;
- указывает существующий route;
- не изменяет Editorial System;
- не утверждает новый permanent workflow;
- не превращает Observation в архитектурное решение.

# 13. Progressive Decision Closure

По мере движения VIA часть решений закрывается.

Закрытое решение не переоткрывается только потому, что следующий Editor предпочёл бы другой вариант.

Переоткрытие допустимо, если обнаружено:

- material theological risk;
- material reader harm;
- фактическая ошибка;
- противоречие DNA;
- невозможность выполнить downstream stage;
- существенная потеря центрального смысла;
- material deviation после Revision;
- новое evidence, отсутствовавшее при первоначальном решении.

Editor, поднимающий вопрос повторно, должен указать:

- какое решение переоткрывается;
- какое новое evidence обнаружено;
- почему локальная коррекция недостаточна;
- кому принадлежит authority следующего решения.

Факт несогласия сам по себе не является material deviation.

---

# 14. Manual Transfer Contract

В текущей рабочей модели Editors являются читателями GitHub, если им отдельно не предоставлено право записи.

Физическое обновление GitHub выполняет Owner.

Рабочая граница:

    System / Editors
    → remembering
    → interpretation
    → routing
    → точный переносимый результат

    Owner
    → необходимое решение
    → физический перенос
    → обновление GitHub / Notion
    → передача следующей ссылки

Owner не должен:

- собирать один результат из нескольких фрагментов;
- восстанавливать место вставки;
- исправлять сломанные Markdown fences;
- самостоятельно вычислять status transition;
- выяснять, какой раздел должен быть заменён;
- заново формулировать routing;
- интегрировать независимые Reviews вместо Coach.

# 15. One Markdown Block Contract

Если результат предназначен для переноса в GitHub, Editor возвращает:

- ровно один внешний fenced Markdown block;
- полный переносимый текст внутри этого блока;
- одну зону копирования;
- корректные Markdown markers;
- текст, готовый к переносу без дополнительной сборки.

За пределами блока не должно находиться текста, который Owner обязан переносить в документ.

Внутри внешнего Markdown-блока запрещены вложенные fenced blocks с тройными обратными кавычками.

Для внутренних технических примеров используются:

- отступ в четыре пробела;
- blockquote;
- таблица;
- маркированный список;
- inline code;
- обычный текст под заголовком `Пример`.

Перед возвратом Editor должен проверить:

- не закрылся ли внешний block раньше времени;
- не появились ли дополнительные кнопки копирования;
- находится ли весь переносимый документ в одной зоне;
- сохранены ли Markdown headings, tables, lists и blockquotes.

Формальная фраза «результат возвращён в Markdown» недостаточна, если визуально ответ разбит на несколько блоков.

# 16. Режимы обновления GitHub-документа

Допускаются два основных режима.

## 16.1. Full Document Replacement

Используется, если:

- документ небольшой;
- изменения распределены по нескольким местам;
- меняется структура;
- необходимо синхронно изменить несколько разделов;
- частичная замена создаёт риск несогласованности.

Перед блоком или в сопровождающей инструкции указываются:

    UPDATE MODE: FULL DOCUMENT
    TARGET: точный путь файла

Editor возвращает полный документ:

- от первого заголовка;
- до последней строки;
- одним Markdown-блоком.

## 16.2. Complete Section Replacement

Используется, если изменение локально и может быть ограничено цельным разделом.

Указываются:

    UPDATE MODE: SECTION REPLACEMENT
    TARGET: точный путь файла
    REPLACE FROM: точный заголовок раздела
    END BEFORE: следующий заголовок того же или более высокого уровня

Editor возвращает:

- заголовок заменяемого раздела;
- полное содержание раздела;
- последнюю строку раздела;
- без фрагментов соседних секций.

Не допускаются:

- набор разрозненных исправлений;
- замена отдельного предложения без достаточного контекста;
- несколько несвязанных вставок;
- инструкция «добавьте где-нибудь после этого абзаца»;
- сокращённый фрагмент, требующий ручной реконструкции раздела.

Если изменения затрагивают несколько удалённых частей и не могут быть безопасно переданы одним цельным разделом, используется Full Document Replacement.

# 17. Owner Actions

Действия, которые Editor не может выполнить самостоятельно, обозначаются:

`🔴 OWNER ACTION`

Owner Action должен содержать:

- точный target;
- необходимое действие;
- ожидаемый результат;
- при необходимости точную status transition;
- следующий route.

Owner Action не должен требовать от Owner повторного редакционного анализа.

Физический перенос сам по себе не считается избыточной Owner load.

Избыточная Owner load возникает, когда Owner должен самостоятельно выполнить:

- remembering;
- interpretation;
- integration;
- routing;
- восстановление контекста;
- исправление технически непереносимого результата.

---

# 18. Publication

Publication block хранит фактическое состояние публикации материала.

Возможные данные:

- Final Text;
- SEO Publication Package;
- Blogger fields;
- publication date;
- scheduled date;
- public URL;
- GitHub reference;
- rendering check;
- фактический publication status.

Publication state не дублируется в паспорте как Current Stage.

Материал может быть:

- подготовлен;
- размещён в Blogger;
- поставлен в очередь;
- опубликован;
- проверен после публикации.

Эти данные описываются внутри Publication block.

Process Map показывает только рабочее состояние соответствующих publication steps.

---

# 19. Preliminary Close

Close может быть активирован до фактической публичной публикации, если:

- Final Text стабилизирован;
- обязательные Reviews и Revision завершены;
- необходимые final checks выполнены;
- статья размещена в Blogger;
- URL определён или ожидается без содержательного изменения;
- материал поставлен в очередь;
- дальнейшая редакционная переработка не ожидается.

На Preliminary Close можно подготовить:

- финальное название;
- VIA ID;
- GitHub reference;
- scheduled publication date;
- предварительный или фактический URL;
- Portfolio update;
- следующий Portfolio item;
- Notion Update Package;
- content learning;
- process observation;
- learning routing.

Пример:

    ## Close Status

    **State:** Preliminary
    **Publication:** Scheduled
    **Final condition:** подтверждение публичной публикации и проверка URL

При Preliminary Close шаг Close остаётся `0`.

Новый символ или дополнительный статус не создаётся.

---

# 20. Final Close

Close получает `+` только после выполнения final conditions конкретного VIA.

По умолчанию проверяются:

- материал опубликован или выполнено иное утверждённое условие завершения;
- публичный URL доступен;
- publication data зафиксированы;
- material rendering deviation отсутствует либо маршрутизирована;
- Portfolio / Notion Update Package подготовлен, если требуется;
- следующий Portfolio step понятен;
- material learning классифицировано;
- блокирующих открытых вопросов нет;
- Lifecycle Status обновлён `Active → Closed`.

Закрытие VIA означает:

> конкретный редакционный цикл завершён.

Это не означает, что материал никогда больше не может быть изменён.

Дальнейшее существенное изменение требует нового решения, отдельного этапа или нового VIA — в зависимости от масштаба работы.

---

# 21. Observation

Observation может проводиться на протяжении всего VIA.

Она не обязана начинаться только после публикации.

Observation может фиксировать:

- достаточность one-link handoff;
- Owner load;
- необходимость дополнительных объяснений;
- потерю или сохранение capability;
- неясность authority;
- конфликт статусов;
- повторяющийся overlap Reviews;
- material deviation;
- недостаточность документации;
- техническую непереносимость Output;
- необходимость ручной интеграции;
- отсутствие или наличие полезного Close routing.

Observation может оставаться `0` параллельно с другими шагами и завершаться при Final Close.

Не нужно фиксировать:

- каждое нормальное действие;
- отсутствие ошибок;
- полную внутреннюю работу Editor;
- время каждого микрошагa;
- каждую локальную правку;
- ритуальное подтверждение соблюдения Protocol.

Основной принцип:

> Сохранять deviation и потенциально значимый pattern, а не полный журнал нормальной работы.

---

# 22. Learning Routing

VIA Close не внедряет learning.

Он:

- сохраняет evidence;
- классифицирует material signal;
- указывает существующий route.

Coach использует четыре категории.

## 22.1. Article

Знание относится только к конкретному материалу.

Route:

    Article
    → остаётся в VIA

Примеры:

- фактическая функция статьи;
- применённая граница;
- локальный risk;
- решение конкретной Revision;
- material-specific publication deviation.

## 22.2. Content

Знание может изменить понимание корпуса или будущий Portfolio decision.

Route:

    Content
    → Strategy
    → при признании durable content intelligence
    → Notion

Примеры:

- новый Human State;
- новый Life Question;
- изменение Difference;
- continuation;
- coverage change;
- cluster или series signal;
- значимый reader/search language signal.

## 22.3. Role

Знание относится к capability конкретного Editor.

Route:

    Role
    → соответствующий Role Backlog

Примеры:

- повторяющийся дефект Output;
- недостаточная role instruction;
- систематическое превышение authority;
- потеря capability;
- повторяющаяся необходимость Owner explanation;
- подтверждённая потребность в role adjustment.

## 22.4. System

Знание затрагивает:

- несколько ролей;
- VIA Protocol;
- общую архитектуру;
- authority boundary;
- системную документацию;
- повторяющийся межсистемный handoff.

Route:

    System
    → Master
    → IDEAS при достаточном основании

`Development` не является автоматическим следующим шагом VIA Close.

Переход в Development происходит только после существующего Review соответствующего Backlog или IDEAS.

---

# 23. Порог маршрутизации

Observation маршрутизируется за пределы VIA, если выполнено хотя бы одно условие:

- проблема повторилась в нескольких сопоставимых циклах;
- обнаружен material deviation;
- потерян или преждевременно переоткрыт закрытый decision;
- Owner был вынужден вручную интегрировать работу Editors;
- one-link handoff оказался недостаточным;
- проблема затрагивает несколько ролей;
- отсутствующая инструкция создаёт риск повторения существенной ошибки;
- learning изменяет будущий Portfolio или content decision;
- единичный случай имеет высокие последствия для качества, безопасности или целостности системы.

Если порог не достигнут, observation остаётся только в VIA.

Если material signal отсутствует, пустой Learning Routing block не создаётся.

Не требуется добавлять ритуальную строку:

`No system learning.`

---

# 24. Формат Learning Routing

При наличии material signal используется короткий блок:

    ## Learning Routing

    - **Type:** Article | Content | Role | System
    - **Signal:** краткое наблюдение
    - **Evidence:** ссылка на точное место в VIA
    - **Route:** VIA | Strategy | Role Backlog | Master / IDEAS
    - **Reason:** почему signal превышает порог маршрутизации

Один signal получает один primary destination.

Если observation относится преимущественно к одной роли, оно направляется в Role Backlog.

Если observation затрагивает несколько ролей или VIA-wide protocol, оно направляется Master.

Одно observation не копируется полностью одновременно в:

- VIA;
- Role Backlog;
- IDEAS;
- Development.

VIA сохраняет исходное evidence.

Backlog или IDEAS сохраняет:

- краткую формулировку pattern;
- ссылку на VIA;
- необходимое системное значение.

При дальнейшем продвижении Development ссылается на первичное evidence и предыдущую запись.

Так сохраняется provenance без параллельного учёта.

---

# 25. Automation Readiness

Текущая система остаётся ручной.

Automation-readiness достигается не созданием преждевременной автоматизации, а однозначностью существующих сигналов.

Для будущего Orchestrator должны быть понятны:

- VIA ID;
- точный путь файла;
- Process Map;
- статусы шагов;
- зависимости;
- активные capabilities;
- Active Handoffs;
- Output Contract;
- Update Mode;
- Replacement Boundary;
- State Transition;
- Owner Action;
- Next Route;
- ссылки на GitHub;
- точные названия таблиц и properties Notion.

Рабочий критерий:

> Если сигнал может без дополнительной интерпретации выполнить Owner, в будущем его сможет выполнить Orchestrator.

На текущем этапе не создаются:

- API workflow;
- автоматическое изменение GitHub;
- новый машинный язык;
- обязательные YAML envelopes;
- отдельный automation registry;
- автоматические архитектурные решения;
- дополнительный status layer.

Automation внедряется только после подтверждения лёгкости и устойчивости ручной практики.

---

# 26. Ответственность

## Owner

Owner:

- принимает необходимые strategic и material decisions;
- физически создаёт и обновляет GitHub-документы;
- физически обновляет Notion;
- переносит готовые результаты;
- подтверждает публикацию;
- утверждает постоянные изменения системы.

Owner не должен быть ручным интегратором результатов Editors.

## Editorial Coach

Coach:

- открывает или читает актуальный VIA;
- формирует достаточный Editorial Brief;
- определяет необходимые capabilities;
- проверяет зависимости;
- подготавливает article-specific handoff;
- координирует параллельные и зависимые шаги;
- интегрирует Reviews;
- определяет необходимые re-checks;
- готовит точные state transitions;
- проверяет переносимость результата;
- проводит Close;
- классифицирует material learning;
- указывает существующий route.

Coach не изменяет архитектуру Editorial System самостоятельно.

## Specialized Editors

Specialized Editors:

- выполняют назначенную capability;
- соблюдают article-specific boundaries;
- действуют в пределах permanent role documentation;
- возвращают переносимый результат;
- указывают material deviation;
- не изменяют Process Map самостоятельно;
- не переоткрывают систему внутри article task.

## Master Editor

Master:

- рассматривает cross-role и architectural signals;
- проверяет существующие boundaries;
- отличает локальную проблему от system pattern;
- не превращает единичное observation в permanent architecture;
- направляет подтверждённое изменение в существующий Development lifecycle.

---

# 27. Conflict Rule

Если обнаружено противоречие:

## Между Process Map и Active Handoff

Process Map определяет состояние.

Работа приостанавливается до исправления handoff или карты.

## Между VIA и памятью ветки

Действует актуальный GitHub VIA.

## Между VIA Template и настоящим Protocol

Действует настоящий Protocol.

Template должен быть исправлен.

## Между локальным handoff и permanent role documentation

Article-specific scope определяется handoff.

Природа, capability и пределы роли определяются permanent role documentation.

Handoff не может скрыто изменить authority роли.

## Между VIA Observation и permanent documentation

Действует permanent documentation.

Observation остаётся evidence до прохождения установленного пути:

    Observation
    → Pattern
    → Backlog / IDEAS
    → Development
    → Permanent Documentation
    → Validation

---

# 28. Validation настоящего Protocol

Настоящая редакция проверяется:

1. при ближайшем реальном переходе `VIA-2026-018`;
2. при параллельной активации необходимых Reviews;
3. при обновлении Process Map;
4. при подготовке Preliminary Close;
5. при Final Close и Learning Routing;
6. при создании следующего нового VIA по обновлённому Template.

Validation должна установить:

- сохраняется ли one-link capability;
- понятны ли несколько параллельных `0`;
- не возникает ли competing state source;
- уменьшилось ли число ручных синхронных изменений;
- возвращают ли Editors один корректный Markdown-блок;
- достаточно ли article-specific handoff;
- уменьшилась ли необходимость повторять постоянные инструкции;
- может ли Owner переносить результаты без интеграционного анализа;
- работает ли Preliminary Close;
- не дублируется ли learning между VIA, Backlog и IDEAS;
- остаётся ли VIA полноценным case file материала.

До завершения Validation Protocol имеет статус:

`Working Protocol / Validation Required`

После подтверждения практикой статус и версия пересматриваются отдельным решением Owner.

---

# 29. Именование и хранение VIA

VIA именуются:

`VIA-YYYY-NNN.md`

Пример:

`VIA-2026-018.md`

VIA хранятся по году открытия:

- `VIA/2026/`;
- `VIA/2027/`;
- `VIA/2028/`.

Закрытый VIA не удаляется и не превращается в постоянную документацию системы.

Он остаётся:

- историей материала;
- evidence редакционного цикла;
- источником provenance для последующих content, role и system decisions.

---

# 30. Основной принцип

> VIA хранит конкретный редакционный цикл.  
> VIA Protocol определяет общую механику.  
> Process Map хранит текущее состояние.  
> Active Handoff хранит конкретное задание.  
> Role Documentation хранит capability Editor.  
> Close классифицирует material learning.  
> Backlog и IDEAS сохраняют подтверждаемые patterns.  
> Development подготавливает одобренные изменения.  
> Permanent Documentation хранит действующую систему.

Editorial System развивается постепенно:

- сначала реальная практика;
- затем Observation;
- затем Pattern;
- затем проверка;
- затем решение;
- затем Documentation Update;
- затем Validation.

Ни Template, ни отдельный VIA, ни единичное Observation не изменяют Editorial System автоматически.
