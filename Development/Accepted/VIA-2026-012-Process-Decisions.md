# 1. Назначение

Настоящий документ фиксирует решения, принятые по итогам первого полного редакционного цикла VIA.

Документ:

- не повторяет полный анализ Process Review;
- не заменяет фундаментальные документы Editorial System;
- определяет направления дальнейшего внедрения;
- служит основанием для обновления Coach, VIA и связанных редакционных процессов.

Исторический анализ сохраняется в:

`Development/Proposals/VIA-2026-012-Process-Review.md`

# 2. Принятые решения

## 2.1. Стабилизировать Coach

Принять решение о стабилизации документации Editorial Coach на основании:

- первого полного VIA-цикла;
- наблюдений Process Review;
- уже утверждённых записей `DEV-001`–`DEV-004`;
- фактической практики работы редакторов через VIA.

При стабилизации необходимо обновить и согласовать:

- `Editors/Coach/README.md`;
- `Editors/Coach/Prompt.md`;
- `Editors/Coach/Workflow.md`;
- `Editors/Coach/Checklist.md`;
- `Editors/Coach/Constitution.md`;
- `Editors/Coach/Backlog.md`;
- `Editors/Coach/Development.md`.

Документация Coach должна закреплять:

- каноническое определение роли;
- единый формат метаданных;
- работу через один VIA;
- передачу через одну активную ссылку;
- чтение текущего состояния VIA;
- определение следующего этапа;
- правила передачи между редакторами;
- различение экспертного мнения, рекомендации, обязательного изменения и решения Coach;
- порядок завершения и закрытия редакционного цикла;
- полный путь развития роли от наблюдения до валидации.

## 2.2. Интегрировать DEV-001–DEV-004

Не создавать отдельные документы `DEV-001`–`DEV-004`.

Эти решения уже существуют как утверждённые записи в:

`Editors/Coach/Development.md`

При стабилизации Coach использовать их как обязательную основу и не запускать повторное утверждение тех же изменений.

После полной интеграции выполнить предусмотренное самим документом действие:

- удалить завершённые записи из активного Development;
- либо сохранить корректную историческую отметку, если к этому моменту будет утверждён соответствующий порядок архивирования.

## 2.3. Развить VIA как центральный документ цикла

Сохранить VIA как единый источник состояния конкретного редакционного цикла.

Развить VIA и его шаблон, добавив:

- оглавление;
- двухуровневый чек-лист;
- текущий этап;
- следующий этап;
- статус основного текста;
- список связанных документов;
- унифицированные названия редакций;
- отметку о завершении и закрытии цикла.

Даже при будущем появлении связанных файлов VIA остаётся главным документом процесса.

## 2.4. Создать единый паспорт редакторских отчётов

Создать единый минимальный паспорт для отчётов редакторов и экспертных комиссий.

Минимальные поля:

- VIA;
- название материала;
- редактор или коллегия;
- тип работы;
- анализируемая редакция;
- дата;
- статус отчёта;
- краткий итог;
- следующий этап.

Точный путь и форма шаблона определяются при реализации после проверки существующей структуры Templates.

## 2.5. Провести Pilot обновлённого Coach и VIA

После обновления документации Coach и шаблона VIA провести следующий реальный редакционный цикл как Pilot.

Pilot должен проверить:

- достаточно ли одной активной ссылки;
- правильно ли Coach определяет текущий этап;
- понимает ли редактор ожидаемый результат;
- работают ли статусы редакций;
- уменьшилось ли количество ручных пояснений;
- не создаёт ли новый шаблон избыточную административную нагрузку;
- можно ли формально закрыть завершённый цикл.

## 2.6. Выпустить стабильную версию Coach

После успешного Pilot:

- провести финальную проверку согласованности;
- зафиксировать версии и статусы документов;
- обновить навигацию;
- закрыть текущий цикл развития роли;
- обозначить стабильную редакцию Coach.

## 2.7. Создать Longform Editor v2

После стабилизации Coach провести отдельный цикл реконструкции Longform Editor.

Обязательная последовательность:

1. самообзор Longform Editor;
2. независимый обзор Master Editor;
3. интеграция двух обзоров Coach;
4. создание полного комплекта документации Longform Editor v2;
5. Pilot Longform v2;
6. корректировка документации по итогам Pilot.

В качестве источников использовать:

- первоначальный Prompt;
- историю редактора;
- первый полный VIA-цикл;
- Process Review;
- литературные рецензии;
- наблюдения об авторском голосе;
- практику повторной редакции после экспертных заключений.

## 2.8. Включить литературное ревью производных материалов

Принять как направление создание короткого литературного ревью для:

- Telegram;
- Facebook;
- микроформатов;
- будущих производных публикаций.

Проверка должна учитывать:

- сохранение смысла исходной статьи;
- соответствие площадке;
- авторский голос;
- повторы;
- чрезмерную симметрию;
- повторное объяснение уже понятного;
- качество финала;
- уместность конкретного живого образа;
- связь с публикационной серией.

## 2.9. Определить место SEO в цикле

Закрепить SEO как отдельный этап после стабилизации основного текста и до окончательного формирования публикационной экосистемы.

SEO может проверять:

- заголовок;
- описание;
- постоянную ссылку;
- внутренние ссылки;
- серии;
- Telegram;
- Facebook;
- обнаруживаемость публикаций.

SEO не получает права определять:

- богословское содержание;
- авторский голос;
- пасторскую направленность;
- ценность материала;
- предполагаемое духовное воздействие.

Редакционное решение остаётся выше метрик.

## 2.10. Сохранить минимальный режим аналитики

До появления автоматизации использовать ограниченную ручную аналитику.

Допустимо фиксировать:

- факт публикации;
- основные просмотры;
- переходы на статью, если доступны;
- реакции и комментарии;
- заметные различия между форматами;
- качественные наблюдения владельца проекта.

Не внедрять сейчас:

- сложные аналитические таблицы;
- регулярный ручной сбор большого числа показателей;
- трудозатратную атрибуцию;
- оценку духовного воздействия через метрики.

# 3. Решения о сохранении без изменений

## 3.1. Архитектура экспертных комиссий

Не изменять содержательные обязанности:

- Theology Editor;
- Reader Board;
- Literary Editor;
- других действующих экспертных ролей.

Изменения касаются только технического протокола работы через VIA.

## 3.2. Центральная роль VIA

Сохранить принцип:

> Один VIA является единым источником состояния конкретного редакционного цикла.

Связанные документы могут появляться позднее, но не заменяют VIA как центр навигации и состояния.

## 3.3. Историческая целостность решений

Не переписывать прежние Process Review задним числом в свете нового опыта.

Новые наблюдения должны фиксироваться:

- в Backlog;
- в новом Proposal;
- в следующем Process Review;
- в другом документе, предусмотренном архитектурой системы.

# 4. Отклонённые решения

## 4.1. Параллельная структура Reviews

Не создавать отдельную папку или самостоятельную систему `Reviews`.

Для обсуждения использовать:

`Development/Proposals`

Для утверждённых решений использовать:

`Development/Accepted`

## 4.2. Дублирование документации

Не создавать новый документ, если соответствующая функция:

- уже существует;
- закреплена в другом файле;
- уже запланирована в фундаментальной архитектуре;
- может быть реализована обновлением существующего документа.

Перед созданием нового документа выполнять проверку согласованности.

## 4.3. Четвёртый маршрут развития системы

Не создавать новый параллельный маршрут развития помимо уже существующих линий:

- `Development/Proposals`;
- развитие отдельных ролей через их `Backlog.md` и `Development.md`;
- `Constitution/IDEAS.md`.

Разграничение этих маршрутов должно быть позднее закреплено фундаментальным документом.

# 5. Отложенные решения

## 5.1. Разделение VIA на несколько файлов

Отложить разделение большого VIA на отдельные файлы до накопления опыта нескольких редакционных циклов.

Требуется определить устойчивые границы между:

- основным VIA;
- публикационной экосистемой;
- визуальными материалами;
- аналитикой.

## 5.2. Архитектура хранения изображений

Отложить системное решение о хранении изображений до появления устойчивого Visual Workflow.

## 5.3. Полный Visual Workflow

Отложить создание полного нормативного Visual Workflow до накопления практики нескольких циклов.

До этого сохранять действующие рабочие принципы:

- визуал служит материалу;
- по умолчанию создаётся фон для дальнейшей сборки;
- на изображении допускается только название;
- основной текст на изображение не переносится;
- логотип не рисуется без предоставленного файла;
- под логотип сохраняется свободное пространство.

## 5.4. Расширенная аналитика

Отложить расширенную аналитику до появления:

- автоматизации;
- устойчивого набора показателей;
- доказанной практической пользы;
- приемлемой стоимости сбора данных.

## 5.5. Отдельный документ авторского голоса

Отложить создание нормативного документа об авторском голосе In Profundo.

До накопления нескольких циклов:

- сохранять литературные наблюдения;
- сопоставлять их между материалами;
- не превращать единичную удачную особенность в обязательное правило;
- использовать накопленные наблюдения при создании Longform Editor v2.

## 5.6. Системная SEO-политика для всех платформ

Отложить создание полной общесистемной SEO-политики.

На первом этапе определить только место SEO в редакционном цикле и минимальные границы полномочий.

# 6. Принцип пересмотра отложенных решений

Отложенные решения не считаются окончательно отклонёнными.

Они могут быть повторно открыты, если новые редакционные циклы:

- выявят дополнительную практическую потребность;
- дадут новые данные;
- изменят оценку затрат и пользы;
- покажут недостаточность прежнего решения;
- создадут новые технические или архитектурные возможности;
- подтвердят устойчивость предлагаемой модели в нескольких случаях.

При повторном рассмотрении необходимо заново оценить:

- актуальность;
- практическую ценность;
- стоимость внедрения;
- риски;
- соответствие действующей архитектуре;
- согласованность с фундаментальными документами;
- наличие уже созданного альтернативного решения.

Повторное рассмотрение является нормальным развитием Editorial System, а не отменой прежнего решения.

Историческая запись об отложении сохраняется.

Новое решение должно иметь собственное основание.

# 7. Порядок внедрения

## Этап 1. Закрытие первого Review

1. Принять настоящий документ.
2. Обновить паспорт:
   `Development/Proposals/VIA-2026-012-Process-Review.md`
3. Установить:
   - `Статус: Superseded`;
   - `Заменён документом: Development/Accepted/VIA-2026-012-Process-Decisions.md`.
4. Прекратить расширение первого Process Review.
5. Новые наблюдения направлять в следующие рабочие документы.

## Этап 2. Стабилизация Coach

1. Открыть:
   `Editors/Coach/Development.md`
2. Интегрировать `DEV-001`–`DEV-004`.
3. Добавить утверждённые наблюдения первого VIA-цикла.
4. Обновить постоянную документацию Coach.
5. Проверить согласованность всех документов роли.

## Этап 3. Обновление VIA

1. Обновить `VIA/README.md`.
2. Обновить действующий шаблон VIA.
3. Согласовать изменения с Workflow Coach.
4. Добавить чек-лист, этапы, статусы и закрытие цикла.

## Этап 4. Pilot Coach и VIA

1. Открыть новый реальный VIA.
2. Провести цикл по обновлённой документации.
3. Зафиксировать проблемы в Backlog.
4. Подтвердить или скорректировать рабочие решения.

## Этап 5. Стабильная версия Coach

1. Завершить валидацию.
2. Обновить версии и статусы.
3. Закрыть текущий Development роли.
4. Зафиксировать стабильную версию.

## Этап 6. Longform Editor v2

1. Провести самообзор Longform.
2. Провести обзор Master Editor.
3. Передать оба обзора Coach.
4. Создать документацию Longform v2.
5. Провести Pilot.
6. Внести итоговые изменения.

## Этап 7. Последующие улучшения

После основных этапов последовательно рассматривать:

- паспорт редакторских отчётов;
- литературное ревью публикационной экосистемы;
- место SEO;
- Visual Review;
- хранение изображений;
- расширенную аналитику.

# 8. Критерии завершения решения

Решения настоящего документа считаются внедрёнными поэтапно.

Первый блок считается завершённым, когда:

- Process Review закрыт;
- Process Decisions принят;
- DEV-001–DEV-004 интегрированы;
- документация Coach согласована;
- шаблон VIA обновлён;
- проведён следующий Pilot;
- выпущена стабильная версия Coach.

Следующий блок развития начинается с создания Longform Editor v2.
