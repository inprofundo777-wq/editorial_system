# 1. Предмет эксперимента

EXP-002 проверяет, можно ли собрать существующую практику Distribution одного опубликованного материала в лёгкий управляемый процесс:

```text
Published Article
→ Coach Distribution Intake
→ Selected Source Analysis
→ Coach Integration
→ Channel Tasks
→ Channel Production
→ Publication
→ Observation
→ Close
```

Эксперимент проверяет процесс Distribution после завершения Editorial VIA.

Он не проектирует постоянную Distribution System.

---

```text
Notion / Content Intelligence

```

Coach не участвует в Content Portfolio.

EXP-002 начинается только после появления опубликованного Source.

# 3. Основная гипотеза

> Distribution одного опубликованного материала можно провести через один живой документ, одну ссылку и минимальную карту статусов, не заставляя Owner заново формировать задания и переносить контекст между отдельными контейнерами.

Рабочая модель:

```text
Owner
передаёт одну ссылку
        ↓
Coach
читает Published Source
и определяет следующий необходимый шаг
        ↓
Editors
последовательно добавляют результаты
в один DIST-документ
        ↓
Owner
только переносит результат,
меняет статус
и передаёт ту же ссылку дальше
```

# 4. Рабочая гипотеза ownership

## Coach

В EXP-002 Coach проверяется как временный owner Distribution Process в отдельном режиме.

Coach потенциально отвечает за:

- чтение опубликованного Source;
- определение необходимого Analysis;
- выбор нужных компетенций;
- порядок подключений;
- интеграцию результатов;
- формирование Channel Tasks;
- закрытие процесса;
- сбор Observation.

Это экспериментальная функция.

Она не изменяет постоянную роль Coach автоматически.

## Reader / SEO / Strategy

Reader, SEO и Strategy не устанавливаются как обязательный College.

Их участие определяется вопросом:

> какая компетенция действительно необходима для подготовки Distribution этого Source?

Возможные функции:

### Reader

- жизненные точки входа;
- разные состояния аудитории;
- риск повторения одного эмоционального угла;
- узнаваемость постов;
- различие между содержательными входами.

### SEO

- формулировки внешнего intent;
- поисковые входы, пригодные для Distribution;
- связь с canonical article;
- риск неверного обещания;
- возможные evergreen-входы.

### Strategy

- место Source в содержательном корпусе;
- связь с сериями и кластерами;
- баланс ближайшего Distribution;
- какие идеи следует вернуть в Content Intelligence;
- риск превращения всех каналов в повтор одной статьи.

EXP-002 должен показать:

- нужны ли все три роли;
- нужна ли их последовательность;
- могут ли некоторые функции выполняться Coach;
- какой Analysis действительно влияет на Channel Tasks.

# 5. Проверяемые гипотезы

## H1 — One Live Document

Один живой DIST-документ способен удержать весь процесс Distribution одного Source без дополнительных рабочих контейнеров.

## H2 — One Link Handoff

Активный участник может приступить к своему шагу по одной ссылке и статусу `0`, без отдельного восстановления контекста Owner.

## H3 — Coach Ownership

Coach способен владеть Distribution Process в отдельном экспериментальном режиме, не смешивая его с Content Portfolio и Publication VIA.

## H4 — Selective Analysis

Reader, SEO и Strategy могут подключаться только при наличии необходимой функции, а не как автоматически обязательный состав.

## H5 — Coach Integration

Coach способен превратить выбранные аналитические входы в ясный пакет Channel Tasks.

## H6 — Channel Autonomy

Telegram, Facebook, Microformats и Visual способны самостоятельно выполнить Channel Task внутри своей компетенции.

## H7 — Minimal Status System

Статусов `- / 0 / +` достаточно для управления Distribution.

## H8 — Reduced Owner Load

Owner преимущественно выполняет:

```text
получить результат
→ вставить в DIST-001
→ 0 заменить на +
→ следующий - заменить на 0
→ передать ту же ссылку
```

## H9 — Useful Output Routing

Наблюдения Distribution можно разделить без нового общего backlog:

```text
Editor-level
→ Editor Development

Content-intelligence
→ Strategy / Notion

System-level
→ Master
```

# 6. Границы эксперимента

EXP-002 не утверждает:

- постоянную Distribution System;
- постоянное название процесса;
- постоянный Template;
- название `VIA-2`;
- новую роль Distribution Editor;
- обязательный состав Reader / SEO / Strategy;
- постоянный порядок Analysis;
- постоянный состав каналов;
- обязательное производство контента для каждого канала;
- автоматизацию;
- окончательную роль Coach в Distribution;
- включение Distribution обратно в Article VIA.

EXP-002 работает только с одним опубликованным Source:

> «Труд как место ученичества».

# 8. Критерии успеха

EXP-002 считается операционно успешным, если:

1. Published Article принят как закрытый Source без повторного выбора темы.
2. Coach определил необходимый Analysis без содержательной интеграции со стороны Owner.
3. Каждый подключённый Editor смог приступить по одной ссылке и активному статусу `0`.
4. Для движения процесса оказалось достаточно статусов `- / 0 / +`.
5. Результаты последовательно добавлялись в один `DIST-001`.
6. Не потребовались параллельные рабочие документы.
7. Coach смог преобразовать существенный Analysis в ясные Channel Tasks.
8. Подключённые Channel Editors поняли задачу и ожидаемый формат результата.
9. Были подготовлены и опубликованы необходимые Distribution outputs.
10. Owner преимущественно выполнял только рабочий цикл:

```text
получить результат
→ вставить в DIST-001
→ 0 заменить на +
→ следующий - заменить на 0
→ передать ту же ссылку
```

11. Наблюдения удалось разделить на:
    - editor-level;
    - content-intelligence;
    - system-level.
12. Для завершения цикла не потребовалось проектировать постоянную Distribution System.

Один успешный цикл не утверждает постоянный процесс.

# 9. Что наблюдать

## 9.1. Coach Distribution Intake

Зафиксировать:

- смог ли Coach самостоятельно определить следующий необходимый шаг;
- какую роль он выбрал первой;
- почему эта компетенция была необходима;
- какие роли он счёл ненужными на этом этапе;
- потребовалось ли Owner уточнять задачу;
- не переоткрыл ли Coach решения Portfolio или Publication VIA.

## 9.2. Selected Source Analysis

Для каждого подключённого Editor проверить:

- понятен ли активный шаг по одной ссылке;
- понятен ли ожидаемый результат;
- какую уникальную ценность добавил Editor;
- повторил ли он уже имеющийся анализ;
- повлиял ли результат на Channel Tasks;
- можно ли было пропустить эту роль.

Особенно наблюдать порядок и необходимость:

- Reader;
- SEO;
- Strategy.

Не оценивать роль только по объёму результата. Основной вопрос:

> Изменил ли этот вклад качество или точность последующего Distribution?

## 9.3. Coach Integration

Проверить:

- смог ли Coach отделить существенные выводы от необязательных;
- устранил ли дублирование между Editors;
- сформировал ли единый смысловой пакет;
- появились ли конкретные Channel Tasks;
- пришлось ли Owner самостоятельно сводить результаты;
- не превратилась ли Integration в повторную редактуру Source.

## 9.4. Channel Tasks и Production

Проверить:

- достаточно ли задания для Telegram, Facebook, Microformats и Visual;
- нужны ли все четыре направления для данного Source;
- способны ли Channel Editors работать автономно;
- различаются ли смысловые входы между каналами;
- не повторяют ли все outputs одну и ту же формулировку;
- можно ли последовательно добавлять результаты без пустых заранее созданных секций;
- не требуется ли отдельный документ для конкретного канала.

## 9.5. Один живой документ

Наблюдать:

- сохраняется ли один источник рабочего контекста;
- легко ли найти активный шаг;
- не появляются ли повторные заголовки;
- не смешиваются ли Analysis, Tasks и готовые outputs;
- остаётся ли актуальная версия результата однозначной;
- насколько тяжёлым становится документ к Close.

## 9.6. Нагрузка Owner

Зафиксировать:

- сколько дополнительных пояснений потребовалось;
- сколько решений Owner принял вне документа;
- сколько отдельных ссылок пришлось передавать;
- пришлось ли Owner интегрировать результаты;
- какие handoff оказались субъективно тяжёлыми;
- какие механические действия повторялись;
- стала ли фактическая нагрузка ниже текущей ежедневной практики Distribution.

# 10. Что считать системным сигналом

## Editor-level signal

Маршрут:

```text
Editor-level feedback
→ развитие соответствующего Editor
```

Примеры:

- Editor не понял задание своей компетенции;
- нарушил Output Contract;
- вернул неудобный для вставки результат;
- повторил работу другой роли;
- не смог сформировать достаточный канал-специфический output.

Одиночная локальная ошибка Editor не является основанием перестраивать Distribution Process.

## Content-intelligence signal

Маршрут:

```text
Content-intelligence feedback
→ Strategy
→ при необходимости Notion
```

Примеры:

- обнаружен новый жизненный вопрос;
- проявилось новое состояние человека;
- возникла содержательная связь между темами;
- Distribution обнаружил самостоятельную будущую тему;
- Source фактически покрывает дополнительный intent;
- обнаружена необходимость консолидации близких карточек.

В Notion возвращается только новое знание уровня корпуса, но не тексты Distribution.

## System-level signal

Маршрут:

```text
System-level feedback
→ Master
```

Системным сигналом считать:

- повторяющийся разрыв одной и той же передачи;
- невозможность работать по одной ссылке;
- необходимость обязательного параллельного документа;
- недостаточность статусов `- / 0 / +`;
- постоянную необходимость Owner интегрировать результаты вместо Coach;
- конфликт ownership между Portfolio, Publication и Distribution;
- повторяющееся отсутствие необходимой компетенции;
- невозможность однозначно закрыть цикл;
- существенный рост административной нагрузки.

Одиночное наблюдение может считаться системным немедленно только тогда, когда оно:

- блокирует завершение эксперимента;
- нарушает границу между функциональными блоками;
- создаёт расхождение источников истины;
- требует решения уровня архитектуры In Profundo.

# 11. Output Routing

После Distribution Coach разделяет результаты:

```text
Editor-level feedback
→ соответствующий Editor

Content-intelligence feedback
→ Strategy
→ при необходимости Minimal Notion Update

System-level feedback
→ Master
```

В Notion не возвращаются:

- тексты Telegram;
- тексты Facebook;
- микроформаты;
- визуальные задания;
- Channel Tasks;
- Coach Integration;
- история статусов;
- полный Distribution Observation.

Distribution outputs и полная история процесса остаются в `DIST-001` / GitHub.
