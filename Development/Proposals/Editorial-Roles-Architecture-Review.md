# Editorial Roles Architecture Review

## Статус

System-Level Analytical Review.

Документ сопоставляет результаты первого цикла Role Reviews Editorial System In Profundo и формирует общую архитектурную картину редакционных функций.

Документ не является Accepted Decision и сам по себе не изменяет Editorial System.

Его задача — подготовить основание для решений владельца о:

- составе редакционных функций;
- обязательных и селективных ролях;
- точках подключения;
- границах ответственности;
- минимальном редакционном цикле;
- месте Long View;
- сокращении административной нагрузки;
- дальнейшей пересборке постоянной документации.

| Поле | Значение |
|---|---|
| Тип | System Architecture Review |
| Статус | Analytical |
| Дата фиксации | 2026-08-07 |
| Основание | Первый цикл Role Reviews |

---

# 2. Главный архитектурный вопрос

Основной вопрос Editorial System:

> Какие функции действительно нужны In Profundo, где они должны находиться в общем пути материала и какие из них должны подключаться постоянно, селективно или периодически?

Исторически система развивалась через добавление специализированных проверок.

Это позволило обнаружить реальные компетенции, но одновременно создало риск:

```text
новая потребность
→ новая роль
→ новый этап
→ новая передача
→ новый статус
→ новая административная нагрузка
```

Зрелая архитектура должна двигаться в обратную сторону:

```text
реальная задача
→ необходимые функции
→ минимально достаточный маршрут
```

---

# 3. Главный системный вывод

Первый цикл Role Reviews показывает:

> Editorial System нуждается не в максимальном количестве редакторов, а в небольшом производящем ядре, ясном владении функциями и селективной экспертизе.

Необходимо различать:

```text
функция должна быть выполнена
```

и:

```text
отдельная роль должна обязательно участвовать
```

Это не одно и то же.

Например:

- богословская ответственность обязательна;
- полный Theology Review каждого материала не обязательно обязателен;

- discoverability нужна для индексируемой статьи;
- большой SEO Review каждой статьи не нужен;

- понимание читателя важно;
- полный Reader Board каждого материала не подтверждён;

- стратегическая память нужна постоянно;
- Strategy Editor не обязан участвовать в каждом article cycle.

---

# 4. Предлагаемая крупная архитектура

Наиболее зрелая система сейчас выглядит не как длинная последовательность ролей, а как несколько крупных фаз:

```text
1. IDEA / FORMATION
2. DRAFT
3. REVIEW
4. FINAL PREPARATION
5. PUBLICATION
6. DISTRIBUTION
7. POST-PUBLICATION OBSERVATION
```

Каждая фаза имеет собственную задачу и не должна механически разрастаться в отдельную бюрократическую систему.

---

# 5. Фаза IDEA / FORMATION

Первая фаза формирует не текст, а редакционное задание.

В неё могут входить:

```text
Owner / Author
Content Memory
Strategy
SEO
Coach
```

Их функция здесь различна.

## Owner / Author

Даёт исходный импульс:

- вопрос;
- наблюдение;
- идею;
- пасторскую проблему;
- тему;
- исследовательский материал.

## Content Memory

Показывает:

- что уже было опубликовано;
- какие близкие материалы существуют;
- к какой линии относится тема;
- где возможен повтор.

## Strategy

Даёт только необходимый стратегический контекст:

- место темы;
- риск повтора;
- связь с серией;
- новый угол;
- возможное развитие.

## SEO

Подключается только если поисковый контекст действительно важен.

Он может дать:

- реальный поисковый вопрос;
- язык читателя;
- search intent;
- один очевидный search gap.

## Coach

Собирает входные сигналы в одно компактное редакционное задание.

---

# 6. Главный результат первой фазы

Результатом должен быть не набор отдельных сообщений редакторов, а:

**Compact Editorial Brief**

Он должен отвечать примерно на вопросы:

```text
Что пишем?
Почему сейчас?
Какой главный вопрос?
Какой угол отличает материал?
Что уже существует рядом?
Какие ограничения важны?
Какие специальные риски уже видны?
```

Техническое задание не должно писать статью за Longform.

Его задача — обеспечить ясный старт.

---

# 7. Longform как производящее ядро

После Editorial Brief материал переходит к Longform Editor.

```text
Compact Editorial Brief
→ Longform
→ Draft
```

Longform остаётся центральной производящей ролью.

Его уникальная ответственность:

- создать сам длинный текст;
- удержать центральный вопрос;
- построить внутреннее движение;
- соединить человеческое наблюдение, богословскую мысль и литературную форму;
- сохранить голос In Profundo.

Из рассмотренных специализированных ролей именно Longform наиболее явно относится к Core каждого нового длинного материала.

---

# 8. Фаза REVIEW

После Draft начинается не линейная цепочка редакторов, а единый экспертный блок.

Предлагаемая модель:

```text
Draft
   ↓
Selective Expert Review
   ↓
Literary
Theology
Reader Board
Strategy — при необходимости
SEO — при необходимости
```

Ключевой принцип:

> экспертные Reviews должны по возможности выполняться параллельно, а не последовательно.

Это уменьшает:

- число передач;
- число статусов;
- ожидание между ролями;
- ручную координацию;
- риск того, что один Review заранее направит другой.

---

# 9. Risk Routing

Не все роли должны автоматически получать каждый Draft.

До Review Coach определяет типы риска.

Пример:

| Риск / задача | Подключение |
|---|---|
| сложная композиция или литературный риск | Literary |
| новое или чувствительное богословское утверждение | Theology |
| риск ложного читательского восприятия | Reader Board |
| серия / повтор / изменение стратегического места | Strategy |
| search-first / evergreen / discoverability вопрос | SEO |

Таким образом, система маршрутизирует **риски**, а не обязательный список редакторов.

---

# 10. Literary Editor

Literary отвечает за независимую литературную диагностику.

Его Full Review особенно оправдан для:

- новых длинных материалов;
- сложной композиции;
- экспериментального жанра;
- текста с сильной образной или ритмической нагрузкой.

Возможен Local Literary Check, если после Revision изменены только:

- начало;
- завершение;
- заголовок;
- отдельный литературно чувствительный блок.

Не подтверждено, что Full Literary Review должен быть обязательным для каждого материала.

---

# 11. Theology Editor

Богословская ответственность является фундаментальной.

Но система должна различать:

```text
богословская ответственность
```

и:

```text
Full Theology Review
```

Возможная маршрутизация:

### High Risk

Full Theology Review.

### Medium Risk

Local Theology Check.

### Low Risk

Отдельный Review может не потребоваться, если материал производный и не содержит новых богословских утверждений.

Особенно высокий риск:

- действие Бога;
- страдание;
- исцеление;
- молитва;
- спасение;
- грех;
- Святой Дух;
- чудеса;
- категоричная интерпретация Писания.

---

# 12. Reader Board

Reader Board должен оставаться диагностической читательской функцией.

Он особенно полезен для:

- пасторски чувствительных материалов;
- новой аудитории;
- потенциально двусмысленного опыта;
- риска ложного обещания;
- чувства обвинения;
- сложного входа в текст.

Он не является:

- голосованием;
- статистической аудиторией;
- маркетинговой фокус-группой.

Полный Reader Board не должен автоматически участвовать в каждой статье.

---

# 13. Strategy после Draft

Strategy наиболее естественно работает до Draft и на уровне проекта.

После Draft он должен подключаться только при конкретном стратегическом вопросе.

Например:

- статья фактически повторяет предыдущую;
- материал изменил своё место в серии;
- Draft открыл новую линию;
- появился вопрос о разделении материала;
- статья превратилась в стратегически иной тип контента.

Поэтому:

```text
Strategy Pre-Draft
→ сильный режим

Strategy Post-Draft
→ selective
```

---

# 14. SEO после Draft

SEO после Draft также должен быть селективным.

Он может проверить:

- соответствие title содержанию;
- search intent;
- обещание страницы;
- обнаружимость;
- внутренние ссылки;
- поисковый риск.

Но SEO не должен открывать новую тему или расширять статью только потому, что существует соседний запрос.

Главный принцип:

```text
SEO уточняет обнаружимость существующего материала
```

а не:

```text
SEO перепроектирует материал под поиск
```

---

# 15. Coach Integration

После экспертного блока Coach получает все Reviews.

Здесь возникает один из самых важных элементов будущей архитектуры:

**Integrated Review**

Coach не пишет ещё один независимый Review.

Он делает синтез.

Результат должен содержать:

```text
что работает

что обязательно изменить

что рекомендуется изменить

что отклонено или не требует действия

какие конфликты между Reviews существуют

что требует решения Owner

что конкретно передаётся Longform
```

Longform не должен получать пять экспертных документов как пять независимых заданий.

---

# 16. Owner после Review

Owner должен подключаться только там, где есть существенное решение.

Например:

- конфликт Theology и Literary;
- изменение центрального тезиса;
- стратегический поворот;
- изменение серии;
- существенный компромисс голоса;
- публикационный риск.

Не следует возвращать Owner каждую локальную правку.

Цель:

```text
эксперты различают
→ Coach интегрирует
→ Owner решает только существенное
```

---

# 17. Longform Author Revision

После Integrated Review материал возвращается к Longform.

```text
Integrated Review
→ Longform
→ Author Revision
```

Longform не должен механически вставлять исправления.

Он должен:

- понять утверждённое направление;
- переработать нужные участки;
- заново восстановить цельность;
- сохранить голос;
- вернуть новый полный paste-ready Markdown.

Это завершает основную авторскую работу.

---

# 18. Повторные проверки

После Author Revision не должен автоматически запускаться второй полный цикл всех Reviews.

Повторная проверка нужна только там, где существенно изменился соответствующий риск.

Пример:

```text
переписано богословское утверждение
→ Local Theology Check

изменён финал
→ Local Literary Check

переписан чувствительный пасторский блок
→ Local Reader Check
```

Это уменьшает overprocessing.

---

# 19. FINAL как архитектурная граница

После Author Revision и необходимых локальных re-check материал достигает состояния:

**FINAL**

После этого не следует открывать большие содержательные Reviews без действительно серьёзной причины.

Дальше начинается не создание статьи, а подготовка к публикации.

---

# 20. FINAL PREPARATION

На этой фазе параллельно могут работать:

```text
SEO Package
+
Visual
```

## SEO Package

Для стабильного текста:

- SEO title;
- search description;
- slug;
- labels;
- internal links;
- alt при необходимости.

## Visual

Для стабильного материала:

- главный blog visual;
- фон / постер;
- визуальная концепция;
- необходимые изображения.

SEO и Visual не должны начинать содержательную переработку Final.

Если обнаружен серьёзный смысловой риск, вопрос возвращается через Coach, а не решается ими самостоятельно.

---

# 21. Publication Preparation

После Final Preparation материал переходит в техническую публикационную фазу.

Publication Preparation включает:

- установку финального title;
- description;
- slug;
- labels;
- alt;
- внутренних ссылок;
- изображений;
- форматирование;
- публикацию;
- проверку Published URL;
- проверку страницы после публикации;
- отсутствие очевидной блокировки индексирования.

Функция подтверждена.

Окончательный вопрос — нужен ли для неё отдельный Publication Editor — пока остаётся открытым.

---

# 22. Публикация блога как граница

Публикация основной статьи в блоге должна быть реальной границей редакционного цикла.

```text
Article Production
→ Blog Publication
→ Published Page Check
→ Article Cycle Closed
```

Статья не должна оставаться «незакрытой», пока:

- не вышел Facebook-пост;
- не подготовлен Telegram;
- не накопилась аналитика;
- не созданы все микроформаты.

Это разные процессы.

---

# 23. Distribution / Platform Adaptation

После публикации начинается отдельная фаза распространения.

```text
Published Article
→ Telegram
→ Facebook
→ Microformats
→ Platform Visuals
→ другие каналы
```

Это не продолжение литературной Revision статьи.

Это адаптация уже опубликованного материала.

На текущем этапе эту область лучше рассматривать как единый функциональный блок:

**Distribution / Platform Adaptation**

Не следует пока автоматически создавать:

- SMM Editor;
- Telegram Editor;
- Facebook Editor;
- Microformat Editor;

как отдельные архитектурные роли.

---

# 24. Visual внутри Distribution

Visual может иметь два разных режима.

## Blog Visual

Связан с Final Preparation основной статьи.

## Platform Visual

Связан с:

- Facebook;
- Telegram;
- микроформатами;
- другими каналами.

Эти режимы могут использовать один визуальный язык, но не обязательно один и тот же формат.

Окончательная архитектура Visual Editor требует отдельного Review и не должна быть решена здесь.

---

# 25. Post-Publication Observation

После публикации начинается отдельный периодический цикл.

```text
данные
→ накопление
→ Analytics / SEO / Strategy
→ наблюдение
→ возможное следующее решение
```

Сюда могут входить:

- Search Console;
- web analytics;
- platform analytics;
- reader feedback;
- search queries;
- устойчивые реакции;
- состояние серии.

Этот цикл не должен удерживать отдельную статью открытой.

---

# 26. Strategy как постоянная проектная функция

Strategy не является обязательной ролью каждой статьи.

Но Strategy остаётся постоянной функцией проекта.

Она работает через:

- Content Memory;
- Portfolio Review;
- Development Options;
- Series Review;
- стратегическую интерпретацию накопленных данных.

Таким образом:

```text
Strategy
→ persistent project layer

Strategy Article Review
→ selective
```

---

# 27. SEO как двойная функция

SEO также имеет два разных уровня.

## Article SEO

Небольшой:

- pre-draft search context при необходимости;
- post-draft discoverability;
- final metadata.

## System SEO

Периодический:

- Search Analytics;
- Internal Linking Audit;
- Taxonomy Review;
- Legacy Content Audit;
- Indexing Diagnostic.

Это позволяет избежать превращения SEO в тяжёлый обязательный этап.

---

# 28. Long View — историческая функция

Long View Review исторически выполнял сразу несколько задач, потому что специализированные функции ещё не были достаточно разделены.

Внутри Long View могли существовать элементы:

- стратегической памяти;
- оценки повторения;
- SEO;
- развития серии;
- общей оценки дальнейшего потенциала;
- анализа библиотеки.

После Role Reviews эти функции получили более естественные места.

Предварительная карта:

```text
Content Memory
→ Strategy

Portfolio / Development
→ Strategy

Search / Discoverability
→ SEO

текущая интеграция
→ Coach

post-publication signals
→ Analytics / SEO / Strategy
```

---

# 29. Предварительный вывод о Long View

На текущем этапе не подтверждена необходимость сохранять Long View как отдельный обязательный Review.

Предварительная гипотеза:

> Long View был историческим контейнером нескольких функций, которые теперь могут быть распределены между более ясными владельцами.

Это не означает, что Long View нужно немедленно удалить.

До Architecture Decisions следует рассматривать его как:

**Legacy Composite Function under review.**

Нужно проверить:

- остаётся ли в Long View уникальная функция;
- или все его зрелые элементы уже имеют нового владельца.

---

# 30. Coach как интегратор двух ключевых границ

В предлагаемой архитектуре Coach особенно важен в двух местах.

## До Draft

```text
Idea + signals
→ Coach
→ Editorial Brief
```

## После Reviews

```text
Expert Reviews
→ Coach
→ Integrated Review
```

Coach не должен обязательно появляться после каждого отдельного действия.

Это позволяет сделать его реальным интегратором, а не административным посредником.

---

# 31. Один активный документ материала

Для отдельной статьи наиболее перспективна модель:

```text
один рабочий документ
```

В нём последовательно могут появляться:

```text
Editorial Brief

Draft

Expert Reviews

Integrated Review

Author Revision

Final Publication Package
```

Не обязательно создавать отдельный файл на каждый статус или каждый handoff.

Цель — чтобы материал можно было проследить от идеи до публикации без множества параллельных документов.

# 45. Решения, которые почти готовы

Сильную поддержку имеют следующие положения:

1. Longform остаётся основной производящей ролью длинного текста.
2. Coach является интегратором, а не универсальным редактором.
3. Coach особенно нужен перед Draft и после экспертных Reviews.
4. Expert Review должен быть по возможности параллельным.
5. Не все редакторы должны участвовать в каждом материале.
6. Routing должен зависеть от риска и задачи.
7. Strategy наиболее важен до Draft и на уровне проекта.
8. Post-Draft Strategy должен быть селективным.
9. SEO должен иметь небольшой pre-draft и post-draft режим, а не большой постоянный Review.
10. Reader Board не является обязательным комитетом каждой статьи.
11. Longform выполняет Author Revision после единого Integrated Review.
12. Повторные Reviews должны быть локальными.
13. Publication является границей основного article cycle.
14. Distribution является отдельным слоем после публикации.
15. Post-publication analytics является отдельным циклом.
16. Long View не следует автоматически сохранять как отдельный обязательный Review.
17. Один активный документ материала предпочтителен.
18. Ручная административная нагрузка Owner должна снижаться.

# 50. Owner Working Decision — 2026-08-08

По результатам обсуждения Architecture Review владелец принял решение не откладывать запуск редакционной системы до завершения полной архитектурной и технической документации.

На ближайших трёх новых longform-материалах вводится временная эксплуатационная модель.

## 50.1. Принятый рабочий порядок

```text
1. Formation
2. Draft
3. Independent Review
4. Integration
5. Revision
6. Final Check
7. Publication Preparation
8. Publication
9. Distribution
```

Этот порядок используется как практическая рабочая модель, но пока не утверждается как окончательная нормативная архитектура Editorial System.

Редакционные блоки на данном этапе являются разделами рабочего цикла и VIA. Они не создаются как новые постоянные роли или самостоятельные административные процессы.

## 50.2. Состав редакторов

На первых трёх материалах используется расширенный состав редакторов.

Это временное пилотное решение необходимо, чтобы определить:

- какие функции регулярно дают существенный результат;
- где возникает дублирование;
- какие проверки позднее могут стать селективными;
- какие границы ролей требуют уточнения;
- какие ожидаемые результаты необходимо закрепить документально;
- какие редакторские подключения не оправдывают создаваемую ими ручную нагрузку.

Расширенный состав пилота не отменяет предложенный в настоящем Review принцип селективной маршрутизации.

Он является способом получить практические основания для последующей настройки состава редакторов в каждом блоке.

## 50.3. Формат работы

Для каждого материала используется один VIA как основной рабочий документ.

VIA включает:

- краткий паспорт материала;
- разделы редакционных блоков;
- подразделы участвующих ролей;
- исходное редакционное задание;
- Draft и Revision;
- независимые редакторские заключения;
- Integrated Review;
- Final;
- публикационные данные;
- краткие наблюдения по работе цикла.

В ходе работы владелец последовательно переносит результаты редакторов в соответствующие разделы VIA и самостоятельно запускает необходимые роли в установленном порядке.

На данном этапе не вводятся:

- отдельные документы для каждого статуса;
- сложные чек-листы;
- формальная система сигналов;
- подробные протоколы уровней A / B / C;
- отдельная документация редакционных блоков;
- автоматизированная маршрутизация;
- окончательная новая документационная архитектура ролей;
- обязательная ручная микрофиксация каждого перехода.

VIA должен отражать фактическую работу над материалом, а не создавать дополнительный административный слой.

## 50.4. Задача и ожидаемый результат редактора

Каждый редактор получает:

- название текущего редакционного блока;
- материал или его актуальную версию;
- короткое описание своей задачи;
- указание на ожидаемый результат;
- существенные ограничения, если они необходимы.

От редактора ожидается содержательный результат, пригодный для непосредственного переноса в VIA.

На пилотном этапе не требуется превращать каждый редакторский результат в формальный протокол со сложными статусами и служебными полями.

Практический опыт редакторов используется как рабочее основание до тех пор, пока повторяющиеся функции и формы результата не станут достаточно зрелыми для документальной фиксации.

## 50.5. Уровни проверки

Редактор начинает с достаточной первичной проверки материала в пределах своей компетенции.

Если значимого риска не обнаружено, редактор не проводит углублённое исследование только ради полноты отчёта.

Если обнаружена конкретная проблема, редактор может самостоятельно углубить проверку настолько, насколько это необходимо для:

- точной диагностики;
- определения масштаба проблемы;
- подготовки практической рекомендации;
- проверки возможных последствий исправления.

Если дальнейшее углубление требует:

- нового большого исследования;
- изменения центрального тезиса материала;
- выхода за пределы исходного задания;
- привлечения другой специализированной роли;
- существенного решения владельца,

редактор фиксирует необходимость такого углубления в своём заключении и передаёт вопрос Coach или Owner.

Редактор не должен незаметно превращать ограниченную проверку в новое самостоятельное исследование.

Формальная система уровней A / B / C на данном этапе не вводится. Её логика используется как принцип соразмерного углубления проверки.

## 50.6. Независимые Reviews и Integration

В блоке Independent Review специализированные редакторы работают независимо друг от друга и не пытаются заранее создать общее коллективное заключение.

Каждый редактор:

- рассматривает материал в пределах своей компетенции;
- выделяет только существенные наблюдения;
- локализует обнаруженные проблемы;
- указывает направление исправления;
- отмечает необходимость углубления или решения Owner, если она возникла.

Coach получает независимые заключения и подготавливает Integrated Review.

Integrated Review должен:

- сопоставить выводы редакторов;
- устранить дублирование;
- показать совпадающие сигналы;
- обозначить конфликты между рекомендациями;
- отделить обязательные изменения от рекомендательных;
- сохранить центральное намерение материала;
- передать Owner только существенные развилки;
- дать Longform Editor ясное направление Revision.

Coach Integration не является механическим пересказом всех Reviews.

## 50.7. Revision и Final Check

Longform Editor получает Draft и Integrated Review и создаёт новую цельную версию материала.

Revision не должна представлять собой механическое внесение отдельных поправок. Текст пересобирается с учётом принятых решений как единое произведение.

После Revision полный повтор Independent Review автоматически не проводится.

К Final Check подключаются:

- редакторы, чьи существенные замечания были приняты;
- роли, для которых исправления могли создать новый риск;
- Coach;
- Owner — в точках окончательного содержательного решения.

Повторная проверка должна быть локальной и отвечать прежде всего на следующие вопросы:

- устранена ли исходная проблема;
- выполнено ли обязательное направление Review;
- не создало ли исправление нового существенного риска;
- сохранилась ли цельность материала;
- готов ли текст к Publication Preparation.

## 50.8. Publication и Distribution

Publication Preparation включает подготовку:

- SEO package;
- окончательного заголовка;
- description;
- permalink;
- ярлыков;
- внутренних ссылок;
- визуального материала;
- других необходимых публикационных элементов.

Publication включает:

- размещение статьи;
- проверку опубликованной страницы;
- проверку заголовка, ссылок, визуала и metadata;
- закрытие основного редакционного цикла статьи.

Distribution начинается после публикации и ведётся как отдельный блок.

Он может включать:

- Telegram;
- Facebook;
- микроформаты;
- платформенные визуалы;
- дополнительные каналы распространения.

Статья не должна оставаться редакционно незавершённой только потому, что ещё не опубликованы все связанные материалы распространения.

## 50.9. Coach

Действующая документация Coach считается достаточной для временной эксплуатации следующих функций:

- формирование Compact Editorial Brief;
- координация ключевых передач между блоками;
- интеграция независимых Reviews;
- подготовка направления Revision;
- Final Readiness;
- наблюдение за работой редакционного цикла.

Одновременно должен быть подготовлен отдельный Historical and Functional Review of Editorial Coach.

Отсутствие этого Review не блокирует пилотную эксплуатацию, но не позволяет считать окончательно определёнными:

- границы Coach;
- необходимость его участия в каждом блоке;
- отношения Coach и Owner;
- отношения Coach, Strategy Editor и Master-level functions;
- разделение работы Coach с материалом и работы по развитию системы;
- будущую документационную архитектуру Coach.

## 50.10. Статус решения

Настоящее решение является рабочим, а не нормативным.

Оно:

- разрешает начать практическую эксплуатацию;
- устанавливает временный порядок редакционных блоков;
- не превращает предложенную архитектуру в Accepted Decision;
- не требует немедленной переработки документов редакторов;
- не утверждает постоянный обязательный состав каждого блока;
- не закрывает открытые вопросы настоящего Architecture Review;
- не предрешает окончательную структуру modes, Stage Editors и A / B / C;
- не запускает автоматизацию до стабилизации ручного процесса.

Опыт пилотной эксплуатации сначала накапливается в практике, а затем используется для обновления архитектурных и технических документов.

## 50.11. Следующая точка решения

После прохождения трёх материалов необходимо оценить:

- полезность каждого редакторского подключения;
- повторяющиеся формы ожидаемого результата;
- дублирование компетенций;
- ручную нагрузку Owner;
- количество необходимых передач и повторных действий;
- качество Coach Integration;
- оправданность самостоятельных углублений;
- достаточность локальных повторных проверок;
- устойчивость девяти редакционных блоков;
- ясность входов и выходов каждой роли;
- готовность отдельных положений к нормативной фиксации;
- готовность системы к более селективной маршрутизации.

По результатам оценки Owner должен определить:

1. какие положения временной модели подтверждены практикой;
2. какие положения требуют изменения;
3. какие проверки должны быть постоянными;
4. какие проверки должны стать селективными;
5. какие функции следует перенести в основные документы редакторов;
6. какие архитектурные вопросы остаются открытыми;
7. готова ли система к созданию Accepted Architecture Decision.

Только после этой оценки следует принимать решение о создании:

# 51. Финальный вывод

Проведённый Review показывает, что Editorial System уже накопила достаточно практического опыта для перехода от преимущественно линейного представления редакционного цикла к более гибкой блоковой модели.

Наиболее устойчивыми элементами будущей архитектуры являются:

- разделение создания текста и независимого Review;
- Longform Editor как производящая роль;
- независимая работа специализированных редакторов;
- Coach Integration как отдельная функция;
- цельная Revision вместо механического внесения замечаний;
- локальный Final Check вместо автоматического повторения полного Review;
- отдельный блок Publication Preparation;
- разграничение Publication и Distribution;
- один VIA как основной рабочий документ материала;
- развитие документации на основании проверенной практики.

При этом Review не даёт достаточных оснований для немедленного нормативного закрепления:

- постоянного состава редакторов в каждом блоке;
- окончательной системы role-modes;
- формальных уровней A / B / C;
- конструкции Stage Editors;
- автоматизированной маршрутизации;
- новой полной документационной структуры редакторов;
- окончательной роли Coach;
- постоянного места Strategy Editor и SEO Editor на каждом этапе;
- судьбы Long View как самостоятельной конструкции.

Owner утвердил временную эксплуатационную модель для проверки на трёх новых longform-материалах.

В течение пилотной эксплуатации используются:

- девять последовательных редакционных блоков;
- расширенный состав редакторов;
- короткие задания каждой роли;
- заранее обозначенный ожидаемый результат;
- один VIA;
- самостоятельное соразмерное углубление проверки;
- Coach Integration;
- цельная Revision;
- локальные повторные проверки;
- наблюдение без немедленного создания новой нормативной документации.
